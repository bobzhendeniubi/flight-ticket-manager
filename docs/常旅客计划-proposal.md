# 椰岛假期 · 常旅客计划（旅客档案 + 会员积分）Proposal

> 状态：草案 v2（待业务/财务拍板）
> 范围：C 端。代理（B 端）已有佣金/结算体系，不在本计划内。

---

## 〇、双层结构（先说清楚「人」和「账号」是两回事）

我们的业务形态是**一个人付钱、一家人飞**：下单账号（或游客手机号）是买家，真正坐飞机的是订单里的乘机人。所以常旅客体系必须拆成两层：

| 层 | 锚点 | 回答的问题 | 用途 |
|---|---|---|---|
| **旅客档案**（人的维度） | 证件号（`Passenger.documentNumber`） | 这个人飞过几次、什么时候飞、住什么酒店、有什么偏好 | 运营/销售/客服的 CRM 画像 |
| **会员账户**（钱的维度） | 登录账号（`User`） | 这个客户贡献了多少消费、该给什么等级和积分 | 积分、等级、权益 |

两层通过订单天然关联（账号 → 订单 → 乘机人）。**旅客档案是本计划的地基，积分是地基上的玩法**——档案不依赖积分就有独立价值，建议先做。

## 一、旅客档案（核心：把散落的订单数据归拢成「人」）

### 1.1 数据现状：全都有，只是没归拢

逐项对过 schema，画像所需字段**都已在系统里**，不需要新增任何采集：

| 想记录的 | 数据已在哪 |
|---|---|
| 飞过多少次、什么时候飞 | `Passenger` → `Order` → `OrderItem(kind=FLIGHT)` → `FlightSchedule.departureTime`，含舱位 `flightCabin` |
| 花了多少钱 | `Order.paidAmount`（订单级，需定人均分摊口径，见拍板清单） |
| 住什么酒店 | `OrderItem(kind=HOTEL/BUNDLE)` → `hotelRoomTypeId` + `hotelCheckIn/Out`；拼房明细在 `Order.roomAssignment` |
| 床型/拼房偏好 | `Passenger.bedPref`（SINGLE/DOUBLE/TWIN/SHARE_OK）、`singleRoom` |
| 餐食/特殊需求 | `Passenger.mealPreference`、`needsWheelchair`、`needsInfantBassinet` |
| 证照与签证 | 护照有效期 `passportExpiry`、签证类型/有效期 `visaType/visaExpiry`、自备签 `visaExempt` |
| 同行关系 | 同订单的其他 `Passenger`（谁总跟谁一起飞 → 家庭/团体识别） |

问题只有一个：同一个人飞 5 次 = 5 条互不相识的 `Passenger` 行。**档案 = 按证件号聚合 + 落一张画像表。**

### 1.2 数据模型草案

```prisma
model TravelerProfile {
  id             String       @id @default(cuid())
  documentType   DocumentType
  documentNumber String
  fullName       String          // 最近一次出现的姓名
  chineseName    String?
  // ── 聚合统计（订单完成时增量更新 + 每夜全量校准）──
  tripCount      Int          @default(0)   // 飞行次数（按去程班次计）
  firstTripAt    DateTime?
  lastTripAt     DateTime?
  totalSpendCny  Decimal      @default(0) @db.Decimal(12, 2) // 人均分摊口径
  // ── 偏好快照（取历史众数/最近值）──
  prefCabin      CabinClass?
  prefBed        String?         // bedPref 众数
  prefMeal       String?
  prefSingleRoom Boolean      @default(false)
  hotelHistory   Json         @default("[]") // [{hotelName, roomType, checkIn, nights}]
  companions     Json         @default("[]") // [{documentNumber, fullName, tripCount}]
  // ── 关联 ──
  linkedUserId   String?         // 本人注册的账号（证件号匹配 SavedPassenger 时回填）
  mergedIntoId   String?         // 人工合并（同人换证：身份证↔护照）指向主档案
  notes          String?         // 运营手工备注（口味、忌讳、服务提示）

  @@unique([documentType, documentNumber])
  @@index([fullName])
  @@index([lastTripAt])
}
```

设计要点：

- **聚合表是缓存，订单是真值**：统计字段可随时由订单全量重算，不怕算错，改口径也能重跑。订单完成事件增量更新 + 每夜定时校准。
- **换证合并**：同一个人身份证下过单又用护照下单会产生两条档案，给后台一个「合并」按钮（`mergedIntoId`），不做自动猜测。
- **历史回溯**：上线时全量扫一遍存量订单即可建出所有档案，第一天就有完整历史，不用冷启动。

### 1.3 后台呈现（admin-web 新增「旅客」板块）

- **列表页**：按姓名/证件号搜，可按「飞行次数、最近出行、消费额」排序筛选 → 运营一眼找出高频客。
- **详情页**：出行时间线（每次航班/酒店/房型）、偏好卡片（床型/餐食/轮椅/单住）、同行人网络、证照有效期。
- **可运营的钩子**（档案独立于积分就能用的价值）：
  - 护照/签证**快到期提醒** →「该续护照了，顺便看看今年的班期」是最自然的召回话术；
  - 去年同期飞过的人 → 淡旺季精准召回名单（导出给运营发微信）；
  - 录单时按证件号自动带出历史偏好（床型/餐食预填），老客体验直接变好。

### 1.4 隐私与权限

档案页集中了护照号、出行记录，比单张订单敏感：

- 查看档案详情限运营及以上角色；**导出动作走 `AuditLog`**（复用现有审计体系）；
- 列表/导出默认脱敏证件号（前 2 后 2），详情页可见全号；
- 客户视角（sales-web 会员中心）只展示本人（`linkedUserId` 匹配）的出行记录，不展示同行人分析。

## 二、会员积分（账户层玩法，建立在档案之上）

采用零售业标准的**消费积分制**（不做航司里程制——我们卖套餐，舱位里程没有意义）。积分跟着付钱的账号走：一个妈妈给全家 5 口订票，积分归她，她才是决策人和复购者。

### 2.1 积分获取（Earn）

| 规则 | 建议值 | 说明 |
|---|---|---|
| 基础累积 | 实付 ¥1 = 1 分 | 以 `Order.paidAmount` 结清口径，税费不计 |
| 入账时机 | 订单完成（回程起飞后 T+7） | 不是付款时——留出退改窗口，避免先给分再追讨 |
| 退款回冲 | 按退款比例扣回 | 挂 `Refund` 流水联动；余额可为负 |
| 售后费用 | `adjustmentCny`（改期/换人费）不累积 | 罚金性质的钱不给奖励 |

### 2.2 积分使用（Burn）

| 规则 | 建议值 | 说明 |
|---|---|---|
| 抵现比例 | 100 分 = ¥1（基础 1% 返还率） | 行业常规 0.5%–2%，1% 起步财务压力可控 |
| 单笔上限 | 最多抵订单金额的 10% | 保住现金流和毛利底线 |
| 入账方式 | 计入 `Order.discountTotal` | 复用现有折扣字段，财务导出口径不变 |
| 有效期 | 24 个月滚动过期 | 匹配「一年一度假」复购周期 |

### 2.3 会员等级（贴椰岛品牌）

| 等级 | 门槛（滚动 24 个月实付） | 权益 |
|---|---|---|
| 🐚 椰友 | 注册即是 | 基础累积 1 倍 |
| 🪸 珊瑚会员 | ¥2 万 | 积分 1.2 倍；**候补优先**（`SeatWaitlist` 排序加权） |
| 🐬 海豚会员 | ¥6 万 | 积分 1.5 倍；候补最优先；每年 1 次免费改期 |
| 👑 椰皇会员 | ¥15 万 | 积分 2 倍；专属客服；改期费全免；生日礼遇 |

> 门槛是占位数字，**要用真实订单回测**：拉近 12 个月直客客单价与复购分布，让各级人数大致呈 70/20/8/2 金字塔再定线。

**候补优先是我们独有的硬权益**：包机满座时 `SeatWaitlist` 已经在跑，高等级插队是零成本、高感知的权益。

### 2.4 积分账模型

```prisma
model LoyaltyAccount {
  id            String      @id @default(cuid())
  userId        String      @unique
  tier          LoyaltyTier @default(BASIC) // 命名避开定价的 TierOverride
  pointsBalance Int         @default(0)
  tierValidTo   DateTime?
}

model LoyaltyTransaction {
  id           String        @id @default(cuid())
  accountId    String
  type         LoyaltyTxType // EARN | REDEEM | CLAWBACK | EXPIRE | ADJUST
  points       Int           // 正负皆可
  balanceAfter Int           // 每笔落快照（照抄 PrepaymentTransaction 记账风格）
  orderId      String?
  refundId     String?
  note         String?
}
```

## 三、和现有系统的对接点（都验证过存在）

| 现有能力 | 对接方式 |
|---|---|
| `Passenger`（证件号/偏好/证照） | 旅客档案的聚合源，零新增采集 |
| `User`（手机号/微信登录） | 会员账户 1:1 挂 `User`；档案 `linkedUserId` 回填 |
| 游客免登录下单（`Order.userId=null`） | 档案照建（按证件号，不需要账号）；积分凭 `guestPhone` 注册后 90 天内补登 |
| `SavedPassenger`（unique 证件号） | 档案 ↔ 账号的匹配依据 |
| `CustomerProfile.tags` 手工 VIP 标签 | 迁移为正式等级，标签保留做备注 |
| `Order.discountTotal` / `Refund` | 抵现与回冲，不新开钱路径 |
| `SeatWaitlist` | 候补排序加等级权重 |
| `PricingConfig` 动态定价 | 积分抵现发生在报价之后，两套体系互不污染 |
| `AuditLog` | 档案导出/手工调分留痕 |

## 四、财务口径（需要财务确认）

1. **积分是负债**：按预期核销率计提（行业惯例 60–80%，先按 70%，半年后用真实数据修正）。1% 返还率 × 70% 核销 ≈ 实际成本 0.7% 流水。
2. **抵现记账**：核销进 `discountTotal`，等同现有优惠，不新增科目。
3. **发票**：积分抵现部分不开票（实付口径开票），与六态开票逻辑不冲突。
4. **手工收款兼容**：积分与档案更新都挂「订单完成」事件而非支付回调，不依赖支付自动化，不用等小程序。

## 五、风控

- 积分只在订单完成 + 过退改窗口后入账（源头防刷）。
- 退款按比例回冲，余额可为负。
- 抵现单笔 ≤10%，积分不可转让、不可折现。
- 手工调分（`ADJUST`）与档案合并走 `AuditLog`，仅 ADMIN。
- 同证件号乘机人频繁更换购买账号 → 报表预警（先观察不拦截）。

## 六、分期路线

| 阶段 | 内容 | 说明 |
|---|---|---|
| **M1 旅客档案** | `TravelerProfile` 建表 + 存量订单全量回溯 + admin-web 旅客板块（列表/详情/合并/备注）+ 证照到期提醒 | **不碰钱路径，纯读侧聚合**，风险最低价值最快；上线当天运营就能用 |
| **M2 积分静默积累** | 积分两张表 + 订单完成钩子自动累积 + 近 12 个月回溯 + 后台可查 | 前台不露出，先把账跑对 |
| **M3 前台露出 + 抵现** | 会员中心（sales-web：等级/积分/本人出行记录）、下单抵现、候补优先、改期减免 | 动了 `discountTotal`，需完整回归 |
| **M4 增长玩法** | 老带新赠分、生日分、淡季双倍、录单自动带出偏好、小程序入口 | 等小程序解冻后一起做 |

M1 与积分完全解耦、不改任何现有写路径，建议立即排期。

## 七、拍板清单（动工前必须定的口径）

1. **代理带来的客人给不给积分？**（最大的渠道政策问题）
   - 给 = 平台和代理抢客户关系，代理会反弹；不给 = 客人体验割裂。
   - 建议：**代理单不累积积分**（代理客户的激励由代理做，我们已付佣金）；但**旅客档案不分渠道照建**（画像是内部资产，不涉及利益分配）。→ 需业务方确认。
2. **人均消费口径**：订单总额 ÷ 乘机人数做人均分摊？还是儿童/婴儿按票价权重分摊？建议先简单平摊，档案表可重算不怕改。
3. **返还率 1% / 抵现上限 10% / 有效期 24 个月**——财务确认负债计提。
4. **等级门槛数字**——拉真实订单数据回测后定。
5. **积分历史回溯多久**：建议 12 个月（档案回溯不设限，全量建）。
6. **游客单积分补登窗口**：建议 90 天，凭手机号匹配。
7. **积分抵现与其他优惠是否互斥**（与「已省/让利」叠加规则）。
8. **档案查看权限**：详情页全号证件对哪些角色开放；导出是否需 ADMIN 审批。

## 附：竞品参考基线

| 玩家 | 模式 | 借鉴点 |
|---|---|---|
| 携程超级会员 | 付费会员 + 积分 | 付费会员我们体量还不到，不做 |
