## 看门狗

### 检查什么

| 项 | 规则 | 级别 | 可调参数（`/opt/ftm/.watchdog.env`） |
|---|---|---|---|
| ① 探活 | 两套 `/healthz` 连续两次（隔 15 秒）失败 → `docker restart` 对应 backend → 30 秒后再探。恢复了记一次「自愈」事件；仍不行报严重 | 严重（自愈成功为警告） | `HEALTH_TARGETS` |
| ② 磁盘 | `/` 与 docker 根目录（同一分区只报一次）≥80% 警告、≥90% 严重 | 警告 / 严重 | `DISK_WARN_PCT` `DISK_CRIT_PCT` `DISK_PATHS` |
| ③ 备份 | 最新一份超过 26 小时 → 严重；最新一份不到上一份 50% → 警告。`.dump` 与旧 `.sql.gz` 都认；2 分钟内还在变的文件（正在写）不算 | 严重 / 警告 | `BACKUP_TARGETS` |
| ④ 容器 | 两栈 12 个容器：不存在 / 没在运行 / 正在重启 / unhealthy（隔 20 秒复查一次，避开发版重建的中间态）；60 分钟内自动重启 ≥3 次报「反复重启」，容器重建后重新计 | `*-staging` 警告，其余严重 | `WATCH_CONTAINERS` `RESTART_WINDOW_MINUTES` `RESTART_ALERT_COUNT` |
| ⑤ docker | `docker info` 20 秒没返回 → 严重，本轮跳过容器检查 | 严重 | `DOCKER_TIMEOUT_SECONDS` |

`/healthz` 只看进程活着、不查库，所以数据库短暂重启不会让看门狗去重启 backend。

附件（blob）备份上线后，在 `BACKUP_TARGETS` 里给它加一个目标（格式和两种产物的填法见
`infra/staging/watchdog.env.example`）：`infra/staging/backup-blobs.sh` 是目录镜像，成功后写
`/opt/ftm/backups/blobs/.last-success` 标记，所以填 `附件|/opt/ftm/backups/blobs|.last-success|26|0`。
附件从数据库迁出的那天，数据库快照会骤降，看门狗会报一次「不到上一份 50%」，第二天自动恢复，属预期。

### 什么时候推、推几次

- **新出现**：立即推。
- **持续中**：最多每 6 小时再推一次（「已持续 X 小时」），其余轮次只记状态不推。
- **警告升到严重**：立即推（「升级」）。
- **条件消失**：推一次「恢复」，带持续了多久。
- **一次性事件**（如自愈重启成功）：同类 6 小时内只推一次，其余计数，下次推送带上「另有 N 次」。
- 一轮里的多条**合成一条**推送；超过企业微信 2048 字节就按行截断，结尾提示去看日志。
- **推送失败**（网络 / 机器人拒收）：内容进 `state.outbox`，下一轮一起补发（最多留 30 行）。
- 状态文件 `/var/lib/ftm-watchdog/state`。删掉它 = 所有还在的问题下一轮当新告警重推一遍。

### 配推送（目前实测机上没配，任何告警都没人收到）

### 验证（只看不动手）

```bash

```

照常检查并逐项打印（磁盘多少、最新备份是哪一份、每个容器是否正常），不重启、不推送；本应推送的
内容原样打印出来。状态记在单独的 `state.dry-run`，不影响正式那份。

### 维护标记

恢复数据库、重建 postgres / redis 这类**会故意停服务**的操作，先挂标记，免得看门狗把停掉的 backend 又拉起来：

```bash
touch /opt/ftm/.watchdog.pause   # 暂停探活 / 自愈 / 容器检查（磁盘、备份照查）
# …维护…
rm -f /opt/ftm/.watchdog.pause
```

标记只管 120 分钟（`WATCHDOG_PAUSE_MAX_MINUTES`）：挂久了自动失效并推一条「维护标记已挂 X 分钟」，
防止忘了摘、监控悄悄停掉。两套环境共用这一个看门狗、这一个标记。

### 日志

`/opt/ftm/backups/watchdog.log`：一切正常时不写；告警 / 恢复 / 自愈 / 推送失败 / 维护中，以及每天一次的
「未配置推送」才写。

## pg_stat_statements（慢查询）与数据层日志上限

### 改了什么

- `docker-compose.prod.yml` 的 postgres 加启动参数：
  - `shared_preload_libraries=pg_stat_statements`：预加载后视图才有数据；
  - `pg_stat_statements.track=top`：只统计客户端直接发来的语句；
  - `log_min_duration_statement=1000`：超过 1 秒的语句写进 postgres 日志；
  - `log_parameter_max_length=0`：慢日志**不带参数值**——护照照片 base64、证件号不进日志，也撑不爆
    日志（容器日志本来就是 json-file 3×50MB 轮转封顶）。本地实测：1.2 秒的语句记成
    `execute <unnamed>: SELECT … $1`，参数值一处都没出现；0.2 秒的不记。
- 迁移 `20260925100000_pg_stat_statements` 建扩展（backend 启动时 `prisma migrate deploy` 自动跑）。
  只有超级用户能建：线上 / 测试容器里 `ftm` 是超级用户，会建上；本机 brew 的 `ftm` 不是，迁移打一条
  NOTICE 跳过、照样记为已应用。
- `infra/staging/pg-top-sql.sql`：现成的 Top SQL 查询。
- 同一批还给 sales-web / admin-web（50m×3）和 redis（20m×3）的容器日志加了上限，此前不设上限、
  只靠发版重建清零（admin-web 的 nginx 访问日志约 14MB/天）。两个前端每次发版都会重建，自动生效；
  redis 和 postgres 一样要单独重建。

### 为什么要单独重建 postgres / redis

编排配置只对**新建的**容器生效。`deploy.sh` 在 postgres / redis 已在跑时带 `--no-deps`，**不会**顺带
重建它们——不带的话，compose 会在拉起 backend 时顺手重建配置变了的依赖（本地实测过），发版就变成
数据库意外中断。所以要在低峰单独做一次，中断几秒。没做之前，每次 `deploy.sh` 结束都会提示
「postgres / redis 的编排配置已变更、容器还是旧的」。

迁移建扩展和重建容器谁先谁后都行：没预加载时扩展照样能建，只是视图查不了。

### 低峰重建（两栈各做一次，各停几秒）

实测：

```bash
touch /opt/ftm/.watchdog.pause
cd /opt/ftm
docker compose -p ftm -f docker-compose.prod.yml --env-file .env.prod up -d --no-deps postgres redis
docker compose -p ftm -f docker-compose.prod.yml --env-file .env.prod ps postgres redis        # 等两个都 (healthy)
docker exec ftm-postgres-prod psql -U ftm -d ftm -Atc "SHOW shared_preload_libraries"         # → pg_stat_statements
docker inspect -f '{{json .HostConfig.LogConfig}}' ftm-redis-prod                                # → max-size 20m
curl -s https://api.citurtravel.com/readyz                                                      # → {"status":"ok",…}
rm -f /opt/ftm/.watchdog.pause
```

测试：

```bash
touch /opt/ftm/.watchdog.pause
cd /opt/ftm-staging
docker compose -p ftm-staging -f docker-compose.prod.yml --env-file .env.staging up -d --no-deps postgres redis
docker compose -p ftm-staging -f docker-compose.prod.yml --env-file .env.staging ps postgres redis
docker exec ftm-postgres-staging psql -U ftm -d ftm -Atc "SHOW shared_preload_libraries"
curl -s https://test-api.citurtravel.com/readyz
rm -f /opt/ftm/.watchdog.pause
```

- backend / worker **不用重启**：
  - Prisma 会自己重连。本地实测 postgres 重建瞬间只有 1 次 `P1017 Server has closed the connection`，
    下一秒的查询就正常了。
  - redis 开着 AOF，队列数据（锁位过期、座位超时释放这类延迟任务）在卷里，重建不丢。BullMQ 的专用连接
    （`maxRetriesPerRequest: null`）会等到重连；通用连接重试 3 次，重建那一两秒里可能有个别请求失败。
  - readyz 连着两次都 503，才需要 `docker compose -p … restart backend worker`。
- `up -d --no-deps postgres redis` 的输出里要看到 `Recreate`；只显示 `Running` 说明这个目录的 compose
  文件还不是新版（测试目录可能在别的分支，先 `git log -1 -- docker-compose.prod.yml` 看一眼）。
- 数据都在命名卷里，重建容器不丢数据。

### 查 Top SQL

```bash
docker exec -i ftm-postgres-prod psql -U ftm -d ftm < /opt/ftm/infra/staging/pg-top-sql.sql
```

三张榜：① 总耗时 Top 20（最该优化的）② 单次平均最慢 Top 20（至少调用 5 次）③ 读盘最多 Top 10
（缺索引 / 扫大表的嫌疑）。统计从上次重置或 postgres 重启起累计；SQL 里的常量已抽成 `$1`，不含客人数据；
每晚 pg_dump 的 `COPY … TO stdout` 已剔掉。优化上线后想从零看效果：`SELECT pg_stat_statements_reset();`

慢日志（单条超过 1 秒）：

```bash
docker logs --since 24h ftm-postgres-prod 2>&1 | grep 'duration:'
```

### 注意

- 本机 `docker-compose.yml` / `docker-compose.test.yml` 的 postgres 没加预加载，不影响：迁移照样通过
  （扩展能建、视图不查），集成测试的清表只枚举基表、不碰扩展的视图。CI 只跑单测，不连库。
- **实测快照从此带这个扩展。** 在本机 brew（`ftm` 不是超级用户）恢复实测 `.dump` 时，`pg_restore`
  会报 2 个错（建扩展没权限、给扩展写注释找不到扩展）并以退出码 1 结束——数据其实已完整恢复。想干净
  地恢复（退出码 0，`set -e` 的脚本也不会断），先把这两项从目录里滤掉：

  ```bash
  pg_restore -l ftm_YYYYMMDD_HHMMSS.dump | grep -v pg_stat_statements > /tmp/list.txt
  pg_restore --no-owner -L /tmp/list.txt -h 127.0.0.1 -U ftm -d <本地库> ftm_YYYYMMDD_HHMMSS.dump
  ```

  本地按非超级用户实测：过滤后退出码 0，逐表行数与源库一致。

## 备份

### 每日快照怎么做（`infra/staging/backup-db.sh`，03:30）

1. **空间预检**：剩余空间不足「上一份快照的 2 倍」（且不少于 2GB）就不导出、非 0 退出。
   07-02 盘满让 Postgres 连续 PANIC 过，备份自己不能成为写满盘的那一下。
2. **导出**：`pg_dump -Fc`（自定义格式，自带压缩），先写 `ftm_YYYYMMDD_HHMMSS.dump.partial`。
3. **两道校验**：`pg_restore --list` 读目录 + 整份读一遍输出到 /dev/null。只看目录不够：经管道导出的
   `-Fc` 目录在文件头，截断的文件照样列得出目录（本地实测截到 60% 的文件 `--list` 仍然成功，
   通读才报 `could not read from input file: end of file`）。
4. **转正**：两道都过才改名成 `ftm_YYYYMMDD_HHMMSS.dump`、判 ok。任一步失败：删 `.partial`、写原因、
   非 0 退出，旧快照一份不删（过期清理只在成功之后跑）。
5. **清理**：保留 14 天，同时清 `ftm_*.dump` 和旧的 `ftm_*.sql.gz`；只扫 `/opt/ftm/backups` 顶层。
   附件备份子目录、`ftm-pre-*` 这类手工快照一概不碰（手工快照要自己删）。

`.partial` 不匹配 `ftm_*.dump`，看门狗和本机拉取永远拿不到半截文件。`refresh-staging-db.sh` 顺手导出的
`ftm_*.sql.gz` 也在这个目录，同样算一份快照、同样按 14 天清。

`/opt/ftm/backups/backup.log` 每次一段：开始 → `ok`（大小、表数据项数、用时）→ 清掉了哪些 → 现存几份、
共多大。失败是 `FAILED: 原因`，看门狗第二天会因「超过 26 小时没更新」报严重。

### 附件（blob）备份（`infra/staging/backup-blobs.sh`，03:40）

护照照片 / 收款凭证的字节不在库里，在 docker 卷 `ftm_blob_data`（库里只留 `blob:sha256:…` 引用），
**数据库快照 + 这份 blob 备份才是一套完整备份**。脚本把卷 `rsync -a` 到 `/opt/ftm/backups/blobs`
（不带 `--delete`，只增不减；blob 永不删除），拷完核对文件数才写 `.last-success` 标记。
crontab 安装行、看门狗注册、恢复步骤见脚本末尾注释；整体方案与回填 / 回滚见 `docs/照片出库-方案与上线步骤.md`。

### 手工快照（高风险操作前）

```bash
bash /opt/ftm/infra/staging/backup-db.sh
```

它和每日快照一样进 14 天轮转。要长期留，复制一份改成不以 `ftm_` 开头的名字（如
`ftm-pre-某操作-20260925.dump`）：不会被自动清理，也不会被看门狗 / 本机拉取当成每日快照。

## 恢复

⚠️ 会覆盖库里现有数据。动手前先做一份手工快照（上一节），留条后路。下面以实测为例；测试把目录、
项目名、env 文件、容器名换成 `/opt/ftm-staging`、`ftm-staging`、`.env.staging`、`ftm-postgres-staging`。

### A. 覆盖到现有库（常规）

```bash
# 0) 先留一份当前状态，再挂维护标记（否则看门狗 5 分钟内会把停掉的 backend 拉起来）
bash /opt/ftm/infra/staging/backup-db.sh
touch /opt/ftm/.watchdog.pause

# 1) 停应用，免得边恢复边写
cd /opt/ftm
docker compose -p ftm -f docker-compose.prod.yml --env-file .env.prod stop backend worker

# 2) 恢复。--single-transaction：中途任何一步出错整体回滚，库保持恢复前原样
docker exec -i ftm-postgres-prod pg_restore --clean --if-exists --no-owner --single-transaction \
  -U ftm -d ftm < /opt/ftm/backups/ftm_YYYYMMDD_HHMMSS.dump

# 3) 起应用（backend 启动会自动 prisma migrate deploy），确认就绪
docker compose -p ftm -f docker-compose.prod.yml --env-file .env.prod start backend worker
curl -s https://api.citurtravel.com/readyz

# 4) 摘维护标记
rm -f /opt/ftm/.watchdog.pause
```

### B. 快照早于最近一次迁移（快照之后又上过带迁移的版本）

`--clean` 只删快照里有的对象：快照之后迁移新建的表会原样留着，而 `_prisma_migrations` 已恢复成旧记录，
backend 启动时重跑那条迁移会撞「已存在」起不来。这种情况改成整库重建再恢复（0、1、3、4 步同 A）：

```bash
# 先判断：快照里最新的迁移 vs 库里最新的迁移，不一样就走 B
docker exec -i ftm-postgres-prod pg_restore --data-only -t _prisma_migrations -f - \
  < /opt/ftm/backups/ftm_YYYYMMDD_HHMMSS.dump | grep -oE '[0-9]{14}_[a-z0-9_]+' | sort | tail -1
docker exec ftm-postgres-prod psql -U ftm -d ftm -Atc "select max(migration_name) from _prisma_migrations"

# 2') 替代 A 的第 2 步：整库重建 + 恢复
docker exec ftm-postgres-prod psql -U ftm -d postgres \
  -c 'DROP DATABASE ftm WITH (FORCE)' -c 'CREATE DATABASE ftm OWNER ftm'
docker exec -i ftm-postgres-prod pg_restore --no-owner --single-transaction \
  -U ftm -d ftm < /opt/ftm/backups/ftm_YYYYMMDD_HHMMSS.dump
```

起 backend 时 `prisma migrate deploy` 会把快照之后的迁移补上。

### C. 旧格式 `.sql.gz`（改格式之前的快照）

纯 SQL 只能灌进空库，不能覆盖（0、1、3、4 步同 A）：

```bash
docker exec ftm-postgres-prod psql -U ftm -d postgres \
  -c 'DROP DATABASE ftm WITH (FORCE)' -c 'CREATE DATABASE ftm OWNER ftm'
gunzip -c /opt/ftm/backups/ftm_YYYYMMDD_HHMMSS.sql.gz | \
  docker exec -i ftm-postgres-prod psql -U ftm -d ftm -v ON_ERROR_STOP=1 -q
```

改格式后，最后一份 `.sql.gz` 14 天后自然清掉。恢复到本机 brew 见上文「pg_stat_statements → 注意」。
