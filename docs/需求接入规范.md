# 需求接入规范 · 非技术需求（产品经理视角）

> 把"业务方用大白话提的需求"翻译成可落地、不踩坑的产品方案。
> **来源：赵姐（业务/运营）、财务、票务岗、签证岗、房控、操作部。** 本文件是内部工作规范，默认不进对外/共享文档。

---

## 0. 前提（为什么要这份规范）

### 0.1 业务方（以赵姐为代表）

提的需求有几个**固定特征，必须默认假设**：

- **非技术**：用业务黑话和口头说法，不会用技术/产品术语。
- **表达不清**：不会写清边界、口径、异常分支、以及和现有功能的关系。
- **没耐心**：丢一句就要结果，不会反复澄清。
- **她说的"怎么做" ≠ 规格**：往往只是她现在的笨办法，不是最优解，甚至会和系统打架。

> **结论：绝不照字面直接实现。先用产品经理思维还原真实意图，再用工程师思维落地。**

### 0.2 财务式需求更危险（2026-07-15 审计新增，最反直觉的一条）

回头审了 4-15 → 7-15 约 50 批需求后发现：**四条跨部门口径打架里，三条源头在财务，不在赵姐。**

| | 赵姐式需求 | 财务式需求 |
|---|---|---|
| 长相 | 大白话、说不清、给的是旧系统的笨办法 | 条目清晰、编号规整、术语专业 |
| 直觉 | **常常是对的**（"停用后要能调价再开卖"、"要能锁位"、"只涨20元不要倍率"、"时刻改不了"——每条都指向真问题） | 也是对的 |
| 错在哪 | **错在解法的形状**（硬删、改日期格式、全看备注、收定金才上系统——全是旧系统的形状） | **错在前提已经失效**，而没人回头检查 |
| 为什么危险 | 好识别：一看就知道要翻译 | **格式规整反而不触发警觉**，直接被当成"想清楚了的口径"收下 |

实锤三例：

- 财务说"包机成本**因为涉及实际支付航班款汇率**由财务维护"——而汇率表在**两周前**就被我们按老板"干脆全删了"删掉了。两句话中间隔着我们，两边都不知道对方说了什么。
- 财务说"历史成本**不改前期数据**"——而这条口径依赖的成本快照，生产环境**从来没写过**（唯一写入者是个早已编译不过的回填脚本）。这条口径从提出那天起就没被满足过，也没人告诉财务。
- 财务说"**操作部门人员负责金额录入**"——而成交价是服务端算的，"录入的金额"是另一个数，两个数之间**没有任何一致性校验**。

> **结论：对财务/规整型需求要多问一句"这条的前提今天还成立吗"。**
> 描述清晰 ≠ 想清楚了。越规整的需求，越容易被直接收下。

## 1. 核心心法（一句话）

把她的每条需求当成 **"一个非技术、没耐心、还说不清楚的最终用户的反馈"**：
**先问"她到底想解决什么问题 / 客户在什么场景下要它"，再决定"系统该怎么做"。**

---

## 2. 四步处理流程（每条需求都走一遍）

1. **还原真实意图** —— 剥掉她给的"实现方式"，找背后的业务目标 / 客户场景。
   - 例：她说"升舱让客服来办" → 真实目标是"客户能买升舱"；"客服办"只是当前笨办法 → 应产品化成可售 add-on。
2. **翻译 + 防黑话泄漏** —— 她的业务黑话 ≠ 客户能懂的话。客户面一律换大白话（见 §5）。
3. **对照系统真相校验（关键）** —— 她报的数字、口径、流程，**一律对着真实代码和数据核实，不要信报来的数字**。重点找：会不会重复收费 / 超售 / 亏本 / 少收钱 / 和现有功能打架。
4. **主动 raise 给老板** —— 把发现的风险 + 我的建议讲清楚；会改实现方案的分叉用 AskUserQuestion 让老板拍板。**不默默按字面做，也不直接和她对线。**

---

## 3. 落地时必守（红线）

- 客户视角文案，不泄漏黑话（§5）
- 服务端价格校验，不信前端价
- 真实库存，卖了就扣，别超售
- 费率 / 参数**可配置**，不写死
- 新加价 / 新规则先检查**会不会和已有计价重复**

### 3.1 收到"加个按钮补个字段"，先问这一句

> **这笔钱、这个座位、这间房，在另外三个岗位眼里变了没有？**

这是 2026-07-15 审计里 51 条问题的公约数。需求总是从**一个岗位的界面**提上来的，而钱账、库存账、履约账是**三本分开的账**。满足提需求那个岗位的观感很容易，代价通常是下游某个岗位失明。

反面教材（都是真事）：

- 补收了单住房差 → **房控不知道，还在给这位客人配室友**（我们微信里明明承诺了"房控同步可见"）。
- 录单岗说"联系人就填录入的人" → **发给客服的导出表里"联系人"变成了录单员，电话是一个横杠**，航变时找不到客人。
- 后台强过了重复乘客 → **看开票额度的人不知道**，191 被同一个人吃两口。
- 房控看板改准了物理房间数 → **卖货逻辑没改**，看板显示余量 8、系统照卖第 9 间。

## 3.5 五个反复出现的病（2026-07-15 审计）

51 条问题不是 51 个独立事故，是**五个模式的反复发作**。写代码前对着过一遍：

1. **只修可见的那一半。** 拼房物理口径改了看板没改卖货（还把"两边一致地错"变成"两边不一致"，更危险）；补房差收了钱房控不跟；批量开票补了上限没补状态闸。物理余量早就算好了摆在那儿，就是不接到闸门上。
   → **判据：这次改动动的是"显示"还是"判定"？只动显示的，先问判定要不要跟。**

2. **照抄解法，不照根因。** 业务方报的"现象"基本都是真的（销控不减、导出漏单、时刻改不了，全是实锤 bug），但给的"解法"几乎都是旧系统的形状。**出事的全是我们照抄了解法的地方。**
   → **判据：她说的是"哪里疼"还是"该吃什么药"？只接受前者。**

3. **把"留痕"当成防线。** 手填价 1 元能过、死单能抬总额、房差能重复收——**这些都有审计**。但审计是事后的、发完就不管的、而且在事务外面。
   → **判据：审计不是闸门。能造成钱错的入口，必须有同步的、在事务内的校验。**

4. **新加的列没有消费方。** 定金四列恒空；模版抄了"婴儿同行成人姓名"但**没有乘客类型**这个概念（婴儿占座收全价）；性别在分房编辑器里只是个徽章，不校验。
   → **判据：新字段谁读？读了做什么判断？答不上来就别加。**

5. **传话没传到位。** 汇率是老板说删、财务说要，两边都不知道对方说了什么，中间隔着我们。成本快照是财务以为有、文档写有、生产从来没写。
   → **判据：跨部门口径必须回传对方原话，不要只传结论。**

## 4. 必查风险清单（赵姐式需求高发坑）

| 坑 | 触发信号 | 正确做法 |
|---|---|---|
| 重复收费 | 新"补差/加价"叠在已有按量计价上 | 先看现有怎么算，改成不重叠的模型 |
| 一口价亏本 | "统一 ¥X"套在高价/高星产品 | 改成按产品可配置，给默认值 |
| 超售 | "先卖，座位/库存客服安排" | 接真实库存校验，售罄禁卖 |
| 少收钱 / 口径错 | 订单金额和展示价对不上 | 对账：下单总额必须 = 客户看到的价 |
| 该产品化却"客服办" | "让客服来办 / 手动处理" | 能自助下单的就做成 add-on |
| 写死价格 | 报一个固定数字就完事 | 存成可配置字段 + 默认值 |
| 黑话泄漏 | 用了行业内部词 | 客户面换大白话 |

## 6.3 两个让 bug 隐形的机制（2026-07-15 修复批实测）

同一天修 22 条问题时，多个独立的排查各自撞到同样两件事。它们是「为什么这些 bug 能活这么久」的答案。

### 6.3.1 测试在断言实现，不在断言行为

**不是没写测试，是测试把 bug 写死成了「正确行为」。** 三个实例，互相独立：

- **开票筛选**：`it('回程已开：invoiceLeg=return + invoiced=true → returnInvoiced=true')` —— 只断言 **where 落对了列**。而真正的 bug 是它**捞出了一堆没有回程的单**（单程单/酒店单/签证单的 `returnInvoiced` 默认就是 `false`）。**筛选落对列 ≠ 捞对单。**
- **护照导出**：三条既有测试分别写着「被过滤的姓名计入未命中」「无航班订单传了区间一律不命中」—— 那正是要修的 bug，被当成规格钉住了。
- **批量改价**：`if (!body) { done++ }` —— **把跳过计成成功**。进度条走绿不是误导 UI，是它**真的在把跳过的班次报成「成功」**。

**判据：**
> 测试断言的是「代码这么写了」还是「用户得到了对的结果」？
> 前者永远绿，因为它就是代码的复印件。

**做法**：修 bug 前先让测试红——**而且要红在对的地方**。PNR 导出那条的第一次红是**假红**（mock 返回 `undefined` 导致旧代码崩溃，而不是检测到泄漏），把 mock 改成返回真实数据后，红的才是真漏洞。

### 6.3.2 UI 会替 bug 打掩护

订单管理的「出行日期」被前端偷偷收窄成单日查询。为什么没人早点发现？**因为摘要 chip 显示的是收窄后的范围**——填了「起始」→ chip 显示 `= 07-17`，**看起来完全正确**，而列表里躺着 21 号的单。同一批还发现导出文件名有个 `travelTo || travelFrom` 兜底，会把「07-17 起全部」的导出命名成 `07-17_07-17.xlsx`——**文件名撒谎比列表撒谎更难查**。

**判据：**
> 界面上那个「看起来对」的数字/文案，是从**用户输入**来的，还是从**代码内部的中间结果**来的？
> 后者会跟着 bug 一起错，于是永远自洽。

**做法**：筛选器要**回显真实生效的条件**（`出行日期：2026-07-17 起（未设截止）· 命中 143 单`），而不是回显自己刚刚加工过的参数。批量操作要**如实报告**（`已改 18，跳过 12（阶梯班次）`），不许把跳过算进成功。

## 6.4 审计/复核前，先读已经拍过板的文档（2026-07-15，最贵的教训）

2026-07-15 那次回头审计报了 51 条问题。**逐条回代码复核之后，12 条是误报**——而其中最丢人的三条，是**已经正式拍过板的口径被当成了 bug**：

- 报「机票成本两套定义」→ 实际 **Q5 已于 6/15 书面确认**：「采用 ÷总座位 + 空座单列（还是按现行的做法）…**与现行系统口径一致，无需改动**」。代码与该决议完全一致。我们把**保留下来的定价参考列**（单座已售成本）误认成了会计口径。
- 报「机场补贴无字段，只能挤进可负的起降折扣」→ 实际 **Q14 已于 6/11 确认**：「『机场补贴』即『起降折扣』（负数=补贴/减项），**不另开科目**」。可负是设计，不是将就。
- 报「手填价无上限」→ 实际 `SETTLEMENT_PRICE_CAP_CNY = 100_000` 一直在。

**这三条的答案全都白纸黑字躺在 `docs/财务模块-需求与数据依赖.md` 的 Q1–Q14 里。审计前读一遍那份文档，能省掉三条。**

### 规矩

1. **复核任何"这个口径不对"之前，先搜 `docs/` 有没有拍过板。** 拍过的，问题不是代码，是**结论没同步给提问的人**。
2. **代码注释里写着"此口径有意为之，已向 owner 标注"的，不是疏忽，是决定。** 要推翻它得显式拍板，并且**把那句注释一起改掉**——否则下一个人照着注释再改回来。
3. **看似矛盾的两个数，先确认是不是两个东西。** 例：`单座(已售)成本` 是定价保本参考、`单座成本 = 包机/总座位` 是会计口径——**两个数、两个用途，只是 UI 上重名了**。真正该修的是重名，不是算法。
4. **误报的成本不只是白干。** 它会让真问题淹没在噪音里，也会让被误报的人（尤其财务）下次不再认真看我们的结论。

### 反过来：复核也会捞出审计漏掉的

同一轮复核里，**审计清单上没有、但确实在漏钱的两条**是复核时才发现的：

- **退款审批中的资金窗口**：`funds-guard` 的处置黑名单里**没有 `REFUND_REQUESTED`** → 退款单据已建但未完成时，多付可以先转进代理余额，之后退款按快照金额照付 → **收 1500、付出 2000**。
- **改结算价没有行锁** → 两个并发请求改同一单的不同行，各自按陈旧快照重算总额，后写覆盖前写 → `total ≠ Σ items`。

**所以复核不是"验收审计"，是第二次独立审计。** 只核对清单 = 只能证伪，证不了实。

## 6.5 原话必须归档（2026-07-15 血的教训）

反馈走微信 docx 是**既成事实**，两次简化反馈表都失败了（业务方把 4 条问题全堆进一个自由文本框，严重程度勾一个 = 8 件事共用一个严重度 = 没有严重度）。别再试第三次做表——**改在接收端**。

**规矩：每批反馈处理时，把逐字原话 + 日期 + 提出方归档进 `docs/`。**

- 微信 docx / 截图是**临时目录里的文件，会消失**。
- 2026-07-15 回头审 50 批需求时，**6/29 – 7/11 的会话记录已被清理，那一整段（0701、0707、0708 四批、0709 三批、0710、0711）的逐字原话永久丢失**，只能靠 commit message 作二手证据。
- 判断一条需求"当初谁提的、什么口径"，是**改口径时唯一的依据**。没有原话，三个月后没人能说清"这条到底是谁要的、为什么这么定"。

`/feedback-batch` 技能第 2 步（统计归类）应产出并落盘：`docs/反馈存档/<日期>-<来源>.md`，内容 = 逐字原话 + 我们的归类判定 + 拍板结论。**这份存档是内部资料，可以写人名。**

## 7. 真实案例（教材）

- **升舱 / 单人入住那次**：她给"单房差 ¥80/晚、升舱 ¥700/程、客服办"。问题：① 客服办 → 产品化为 add-on；② 单房差和现有按房计价**重复收费** → 改成双人同住 / 单人入住模型；③ ¥80 套五星酒店**亏本** → 改成按产品可配置；④ "单房差"是黑话 → 客户面说"单人入住"。
- **顺手抓到的线上 bug**：因为不信报来的价、对着代码核，发现**套餐下单丢了机票钱**（客户看 ¥10,606、订单只记 ¥5,636、且不扣机票座位）→ 已修复。

### 7.1 2026-07-15 回头审计（4-15 → 7-15，约 50 批）

51 条"照做了但站不住"，其中 24 条会真丢钱/超卖/静默失败。挑几条最有教材价值的：

- **"订单录入错了不能删除，删除后机位和酒店就会自动退回库存到销控"** —— 现象是真的（录错了确实没法处理），但"硬删+自动退库存"这个**解法本身就是错的**：删除不能同时承担取消、退款、释放座位、释放酒店四件事，否则钱账/库存账/审计被一个动作一次绕过。正解是先取消/退款释放库存，再软删隐藏。**这是"顶回去是对的"的范本。**
  教训里更疼的一半：我们当时给的"删除"按钮其实是 `force=true` 的强制取消，**弹窗还写着"不可恢复"（骗人）**，且已收款的单也能删——座位放了、钱留着、不建退款单。**假装满足需求比不满足更糟。**
- **"这个酒店可不可以设 0.5"** —— 0.5 是**算钱**的单位，不是**库存**的单位；酒店给不了半间房。我们把计费口径直接插进库存口径，房控数错了三周，且床位口径永远看不见性别（男女不能拼）。
- **"单住补房差 ¥80/晚"** —— 没人 question 过 ¥80 这个数本身。而且算房间数的函数入参里压根没有"几个人要单住"，2 个成人都勾单住 = 算 1 间、收 ¥160/晚，实际要 2 间五星房。
- **"所有岗位导出都可以带出金额"** —— 这条口径的前提"岗位"**在系统里不存在**：签证岗/房控/操作部/票务全都是 STAFF。于是导出的 role 参数是客户端自己传的，是化妆不是权限。**收到一条口径，先确认它依赖的概念系统里有没有。**
- **"出生日期和证件有效期的格式，日月年行不行？因为我在导入，用的旧系统数据我要改返过来"** —— 理由只是**一次性的迁移便利**，换来的是永久的日期歧义。而证件有效期是"护照够不够 6 个月"这条规则的输入，错了要到值机柜台才发现。

---

**总纲：业务方给的是"问题与诉求"，不是"规格"。先翻译成对的产品方案、把坑挑出来给老板，再落地。**
**财务给的是"看起来像规格的东西"——先验证它的前提今天还成立吗，再落地。**
