# 需求接入规范 · 非技术需求（产品经理视角）

> 把"业务方用大白话提的需求"翻译成可落地、不踩坑的产品方案。
> **主要来源：赵姐 转达 / 提出的需求。** 本文件是内部工作规范，默认不进对外/共享文档。

---

## 0. 前提（为什么要这份规范）

业务方（以赵姐为代表）提的需求有几个**固定特征，必须默认假设**：

- **非技术**：用业务黑话和口头说法，不会用技术/产品术语。
- **表达不清**：不会写清边界、口径、异常分支、以及和现有功能的关系。
- **没耐心**：丢一句就要结果，不会反复澄清。
- **她说的"怎么做" ≠ 规格**：往往只是她现在的笨办法，不是最优解，甚至会和系统打架。

> **结论：绝不照字面直接实现。先用产品经理思维还原真实意图，再用工程师思维落地。**

---

## 1. 核心心法（一句话）

把她的每条需求当成 **"一个非技术、没耐心、还说不清楚的最终用户的反馈"**：
**先问"她到底想解决什么问题 / 客户在什么场景下要它"，再决定"系统该怎么做"。**

---

## 2. 四步处理流程（每条需求都走一遍）

1. **还原真实意图** —— 剥掉她给的"实现方式"，找背后的业务目标 / 客户场景。
   - 例：她说"升舱让客服来办" → 真实目标是"客户能买升舱"；"客服办"只是当前笨办法 → 应产品化成可售 add-on。
2. **翻译 + 防黑话泄漏** —— 她的业务黑话 ≠ 客户能懂的话。客户面一律换大白话（见 §5）。
3. **对照系统真相校验（关键）** —— 她报的数字、口径、流程，**一律对着真实代码和数据核实，不要信报来的数字**。重点找：会不会重复收费 / 超售 / 亏本 / 少收钱 / 和现有功能打架。
4. **主动 raise 给老板** —— 把发现的风险 + 我的建议讲清楚；会改实现方案的分叉用 AskUserQuestion 让老板拍板。**不默默按字面做，也不直接和她对线。**

---

## 3. 落地时必守（红线）

- 客户视角文案，不泄漏黑话（§5）
- 服务端价格校验，不信前端价
- 真实库存，卖了就扣，别超售
- 费率 / 参数**可配置**，不写死
- 新加价 / 新规则先检查**会不会和已有计价重复**

---

## 4. 必查风险清单（赵姐式需求高发坑）

| 坑 | 触发信号 | 正确做法 |
|---|---|---|
| 重复收费 | 新"补差/加价"叠在已有按量计价上 | 先看现有怎么算，改成不重叠的模型 |
| 一口价亏本 | "统一 ¥X"套在高价/高星产品 | 改成按产品可配置，给默认值 |
| 超售 | "先卖，座位/库存客服安排" | 接真实库存校验，售罄禁卖 |
| 少收钱 / 口径错 | 订单金额和展示价对不上 | 对账：下单总额必须 = 客户看到的价 |
| 该产品化却"客服办" | "让客服来办 / 手动处理" | 能自助下单的就做成 add-on |
| 写死价格 | 报一个固定数字就完事 | 存成可配置字段 + 默认值 |
| 黑话泄漏 | 用了行业内部词 | 客户面换大白话 |

---

## 5. 黑话 → 客户大白话对照（持续补充）

| 业务黑话（内部 / 赵姐） | 客户面说法 |
|---|---|
| 单房差 / 单住补房差 | 单人入住（一人一间房） |
| 让利 | 已省 / 立省 |
| 占位 / 锁位（对客户讲时） | 已为你保留 |
| 升舱 | 升级商务舱 |
| 出票 / PNR | 机票已确认（订单状态层面） |

> 后台 / 运营面可保留黑话（受众就是商家）；**只在前台客户面翻译**。

---

## 6. 沟通姿态

- 她脾气大、说不清 → **我对老板把问题和建议讲清楚，不直接怼她**，也不照单全收。
- 内部一定要 raise；对外（若需回她）用她能接受、听得懂的话。

---

## 7. 真实案例（教材）

- **升舱 / 单人入住那次**：她给"单房差 ¥80/晚、升舱 ¥700/程、客服办"。问题：① 客服办 → 产品化为 add-on；② 单房差和现有按房计价**重复收费** → 改成双人同住 / 单人入住模型；③ ¥80 套五星酒店**亏本** → 改成按产品可配置；④ "单房差"是黑话 → 客户面说"单人入住"。
- **顺手抓到的线上 bug**：因为不信报来的价、对着代码核，发现**套餐下单丢了机票钱**（客户看 ¥10,606、订单只记 ¥5,636、且不扣机票座位）→ 已修复。

---

**总纲：赵姐给的是"问题与诉求"，不是"规格"。先翻译成对的产品方案、把坑挑出来给老板，再落地。**
