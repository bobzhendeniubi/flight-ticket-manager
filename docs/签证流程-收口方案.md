# 签证流程收口方案 —— 按签证岗四态流水线重排

> 2026-08-30 拍板方向。起因：两单录成「需要签证 + 全员自备签」的矛盾组合，签证台看不到、
> 送签对不上数；签证岗给出的理想模型是一条流水线，比现状干净，本方案按它收口。

## 一、目标口径（签证岗原话翻译成系统语言）

> 「客人进单是需要签证就进入需要签证选项，自备签单机票就进不需要选项，电子签就进电子签选项，
> 我们送了签的不管是电子签或者单次签，只要确认了就进入已签证。只需要这四个选项。」

补充口径（同日签证岗追加）：

> 「只要是办签证，都是需要签证。如果有除开 15 天单次或者单办签证的特殊情况，
> 有颜色区分或者提示我们就可以。」

确认单回话后的**最终口径**（2026-08-30 晚，签证岗逐条回复）：

- **录单四个选项保留**（不需要/需要/电子签/已签证）——签证岗明确「代理不会选岔，我们现在
  也是这样」，砍两档的提议不采纳，录单下拉**一动不动**。
- **特殊情况彩色徽标**：电子签 / 非 15 天单次 / 纯签证单，由签证产品结构化字段派生；
  **加急不需要单独颜色**（签证岗原话）。
- **已签证的办结写入**：签证岗标「已送签」即算（**材料送出去就算**，签证岗定的时点），
  整单非自备签乘客全部已送签 → 订单自动置已签证。
- **对数口径**：送签人数按**乘客级已送签数**统计（只有我方送签才会有这个标记），
  录单选「已签证」（客人自带）的单不产生送签标记，天然不混入。
- **已送签后客人不办**：是否可退、退多少**由人为确认**（签证岗原话），系统不硬拦也不自动退。
- **混合单**（一单有人办有人自备）：不做新功能，签证台按**单人单独显示**即可（现状即是——
  乘客平铺、自备签乘客不显示）。

## 二、现状 → 新模型映射

| 现状 | 新模型 |
|---|---|
| 订单级 `visaStatus` 四枚举（NEEDED/E_VISA/HAS_VISA/NOT_NEEDED），录单四档可选 | **不动**（签证岗回话保留四档）；「不需要/已签证」联动自备签、否决建任务等既有口径全部保留 |
| 已签证只能录单人手选 | 增加**系统办结写入**：整单非自备签乘客全部标「已送签」→ 订单自动置已签证（留审计、可对称回退）；对数统计按乘客级已送签数，不受录单手选已签证影响 |
| 签证类型靠录单人选「电子签」档 | 电子签/非 15 天单次/纯签证单由签证**产品**结构化字段派生彩色徽标（录单电子签档仍在，徽标是补充展示，两边不打架） |
| 乘客级 `visaSubmissionStatus`（待处理/材料准备/已送签） | 不动。签证岗的「已签证」落在全员 CONFIRMED 的汇总上 |
| 乘客级 `visaExempt`（自备签，挂 ¥240/人） | 不动语义，**收窄露出**：仅混合单（一单有人办有人自备）展开逐位选 |
| 签证任务 VISA_APPLICATION | 不动；「不需要/已签证」不建新任务的否决口径保留（办结单确实不需要新任务） |

存量：实测库 HAS_VISA 订单 **0 条**（448 NOT_NEEDED / 57 NEEDED / 2 E_VISA），无数据迁移。
sales-web / miniprogram 不使用该枚举，改造只涉及 backend + admin-web。

## 三、改造项

### A. 录单不动 + 特殊情况徽标（第一期）

- 录单弹窗/批量创单的签证状态下拉、出行人「随套餐/自备签」下拉**全部保持现状**
  （签证岗回话：四选项保留，代理不会选岔）。既有联动（不需要/已签证→全员自备签）不动。
- 特殊情况徽标：签证台/订单详情按签证产品结构化字段亮彩色徽标——电子签、非 15 天单次、
  纯签证单（无航班）。默认 15 天单次不亮，特殊才显眼；**加急不加色**（签证岗回话）。
  产品字段缺失时沿用现有「·推测」标记，不把弱证据装成权威（此前审计指出过这个坑）。

### B. 「已签证」= 派生办结状态（第一期）

- 时点（签证岗定）：**材料送出去就算**——即现有「已送签」标记（乘客级 CONFIRMED），
  不等出签，不新增状态。
- 触发：签证台标记「已送签」时事件驱动检查——本单非自备签乘客全部 CONFIRMED →
  订单 `visaStatus` 自动写 HAS_VISA（留审计），列表/详情/导出徽标随之变绿。
- 撤销对称：任一乘客从 CONFIRMED 回退 → 订单从 HAS_VISA 回落原档（办结写入时把原档存进
  审计 before 字段，回退时读取）；录单人手选的已签证单没有办结审计记录，不受回退逻辑影响。
- 签证台筛选档**不动**（0828 五档口径刚按签证岗要求上线）。
- 对数：签证台加统计条——当前筛选范围内「已送签 x 人 / 待送 y 人」，x 即签证岗的送签总数。
  按乘客级已送签数统计：只有我方送签才有该标记，录单手选已签证（客人自带）的单不产生，
  数永远对得上。

### C. 已送签改自备的「人为确认」闸（第二期，钱的正确性）

- 现状漏洞：乘客送签进度非 PENDING 后仍可改回自备签，应收**静默**退 ¥240——批文成本已发生，
  没人看见这笔钱退了。
- 口径（签证岗回话）：是否可退、退多少**由人为确认**，系统不硬拦也不自动退。
- 闸门：`visaSubmissionStatus ≠ PENDING` 的乘客改自备签/换人清签证时弹确认：
  - 提示「该乘客已送签，批文成本已发生」；
  - 退费金额**当场填**（默认 0，上限 = 该乘客自备签减免额），必填原因，留审计；
  - 不确认不放行——把今天的静默退变成显式决定。
- 已送签后取消订单同理：退款流程里签证费单列出来让操作人确认，不再默认全退。

### D. 签证价格收敛一处（第二期，可维护性）

- 现状：¥240 散在每个套餐的 `selfVisaDeductCny` + 各签证产品价，改价要挨个套餐改，会漂。
- 收敛：套餐自备签减免额**默认读取**套餐所含签证组件的产品价（240）；套餐显式配了减免额则覆盖
  （留给特价团）。签证产品价上已有加急档位（240 不加急 / 350 加急），继续做唯一价格源。
- 节假日价：暂走「补收杂费」手工通道（现状即可），需求坐实后再加日期区间价，不预建。

### E. 防呆（第一期，随 A 顺手）

- 录单/编辑出现「需要签证 + 全员自备签」矛盾组合 → 琥珀提示「本单不会进签证台」，
  可提交但必须看见（本次两单事故的直接教训）。

## 四、分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| 一期 | B 办结派生 + 统计条 + A 徽标 + E 防呆 | 签证台标完「已送签」订单自动变已签证、回退对称；统计条人数=送签数；特殊签证类型有徽标（加急无色）；矛盾组合有提示；`npm run build` 双端 + 后端测试绿 |
| 二期 | C 人为确认闸 + D 价格收敛 | 已送签乘客改自备签弹确认、退额当场填且留审计；改签证产品价一处、套餐减免额跟随；单测覆盖钱路径 |

- 录单 UI 零改动（四选项保留），无需知会代理。
- 部署顺序：一期先上（纯口径，无钱风险），实测冒烟后再上二期（动钱，先测试环境过一轮）。
- 上线知会：只需告知签证岗两句话——标完已送签订单会自动变已签证；已送签的人改自备签会弹退费确认。

## 五、不做的

- 不动乘客级 `visaExempt` 的定价语义（服务端永不静默改钱，2026-08 拍板口径不变）。
- 不做假设性的节假日价格引擎（先手工通道，需求坐实再建）。
- 不追既往：本方案上线前按旧口径录的单不批量重算钱。

## 六、状态机（2026-09-06，审查根因 R3 的结构投资）

> 代码：`backend/src/modules/fulfillment/visa-state.ts`（派生 + 转移表 + 唯一写点）；
> 口径台账：`visa-rulings.test.ts` / `visa-rulings.service.test.ts`（0827 / 0830 / 0901 / 0903 / 0904 逐条钉死，收拢前后一条不能红）。
> **不加任何 schema 列**：状态是从既有三列派生的，落库仍是那三列。

### 6.1 状态（乘客级，六态）

| 状态 | 含义 | 对应事实 |
|---|---|---|
| `NOT_NEEDED` | 订单级「不需要签证」（0827 联动全员自备签属于此态，跟订单头） | `Order.visaStatus=NOT_NEEDED` |
| `SELF_ARRANGED` | 客人自备签，不进签证台、不计数、导出金额 0 | `Passenger.visaExempt=true` |
| `PENDING` | 我方代办·待处理（≈ AWAITING_DOCS） | `visaSubmissionStatus=PENDING` |
| `IN_PROGRESS` | 我方代办·材料准备（≈ DOCS_READY） | `visaSubmissionStatus=IN_PROGRESS` |
| `SUBMITTED` | 我方代办·已送签（「材料送出去就算」0830） | `visaSubmissionStatus=CONFIRMED` |
| `ISSUED` | 已签证：录单手选的客人自持，或全员已送签自动办结 | `Order.visaStatus=HAS_VISA` |

**派生事实**（`PassengerVisaFacts`）：`orderVisaStatus` × `visaExempt` × `visaSubmissionStatus` × `allPassengersExempt`
（最后一项订单级算一次：全员置上 = 录单联动，混合单里的自备签是逐人手勾的）。

**派生优先级**（`derivePassengerVisaState`，与导出「签证状态」列逐字一致，0904 拍板）：
1. 逐人推进的送签进度压过一切（IN_PROGRESS / SUBMITTED）——「逐人事实压过订单头」
2. 订单级 `NOT_NEEDED` → `NOT_NEEDED`（联动置上的自备签跟订单头，不写「自备签」）
3. 订单级 `HAS_VISA` → 混合单里逐人手勾的自备签写 `SELF_ARRANGED`，其余 `ISSUED`
4. `visaExempt` → `SELF_ARRANGED`
5. 其余（NEEDED / E_VISA / 未表态）→ `PENDING`

### 6.2 事件与转移表（`transitionPassengerVisa`，纯函数，守卫文案只定义一份）

| 事件 | 触发点 | 守卫 | 写入 |
|---|---|---|---|
| `DECLARE_NOT_NEEDED` | 录单 / 改备注 / 改单申请 VISA / 代理自助 | 订单级矛盾闸 `assertNoVisaContradiction`（0901） | `Order.visaStatus=NOT_NEEDED` |
| `DECLARE_NEEDED{NEEDED\|E_VISA}` | 同上 | 同上 | `Order.visaStatus=NEEDED / E_VISA` |
| `DECLARE_HAS_VISA` | 签证岗盖章 / 系统办结（代理 403 在路由层；改单申请排除，待拍板） | 同上 | `Order.visaStatus=HAS_VISA` |
| `DECLARE_SELF_ARRANGED{submittedConfirmed}` | 改自备签 / 改单申请 VISA_EXEMPT | 进度 ≠ PENDING 须人为确认（`NEED_CONFIRM_SUBMITTED`，0830 二期 C） | `visaExempt=true, 进度=PENDING` |
| `REVOKE_SELF_ARRANGED` | 改回随团办签 | — | `visaExempt=false, 进度=PENDING`（连已确认的进度也回落） |
| `UPLOAD_PASSPORT` | 护照补录 | — | 无（缺件由 `passportPhotoUrl` 单独判定） |
| `MARK_DOCS_READY` | 签证台标材料准备 | 非自备签（`SELF_ARRANGED`） | `进度=IN_PROGRESS` |
| `SUBMIT` | 签证台标已送签 | 非自备签 | `进度=CONFIRMED` |
| `REVERT{to}` | 签证台退回 | 非自备签 | `进度=PENDING / IN_PROGRESS` |
| `SWAP_PASSENGER{visaExempt?, documentChanged}` | 换人 | — | 显式带值 > 真换人回落 false > 保持；**进度不动**（现状） |
| `SPLIT_MOVE` | 拆单 | — | 无（状态随人走，乘客保 id 整行搬家） |

订单级四档 → 声明事件的唯一翻译：`orderVisaDeclarationEvent`；签证台目标档 → 事件：`visaProgressEvent`。

### 6.3 派生（乘客态 → 订单级 / 任务级）

- **订单级办结** `deriveOrderVisaStatus`：非自备签乘客**全部** `SUBMITTED`、至少一位、确有我方任务 → `HAS_VISA`；否则回落声明档。
  回退对称由 `visa-completion` 按审计（`AUTO_COMPLETE_VISA` / `_REVERT`）判来源；录单手选的已签证不回退；回退会造出矛盾单时保持已签证。
- **任务级状态** `deriveVisaTaskStatus`：= 非自备签乘客进度的**最低档**（无人可送 → PENDING）；`CANCELLED / FAILED` 是任务独有终态，派生永不复活。
- **任务的有无**不归状态机：仍由 `orders/visa-need.ts` 的 `orderNeedsVisaTask`（三根轴收口）判定、`syncVisaTasksForOrder` 执行。

### 6.4 与五个真值源的映射

| 真值源 | 在状态机里的角色 | 唯一写点 |
|---|---|---|
| ① `Order.visaStatus` | 声明档（DECLARE_*）；办结派生写 HAS_VISA | `writeOrderVisaStatus`（noteData 同一条 UPDATE） |
| ② `Passenger.visaExempt` | SELF_ARRANGED 的事实 | `writePassengerVisaExempt`（换人的身份列走 extra 同一条 UPDATE） |
| ③ `Passenger.visaSubmissionStatus` | PENDING / IN_PROGRESS / SUBMITTED 的事实 | `writePassengerVisaProgress`（按人 / 整单两种形态） |
| ④ `FulfillmentTask(VISA).status` | 派生物（最低档） | `rederiveVisaTaskStatus`（touch 集合由调用方给）；换人重置 `resetVisaTaskProgress` |
| ⑤ 套餐签证组件 + `selfVisaDeductCny` | 定价输入，**状态机不碰钱**（服务端永不静默改价） | —（改自备签的钱路径在 `setPassengerVisaExempt` 自己算） |

**建单两处仍直写①②**（`createOrder` 的 `order.create` 与 `passengerToData`、拆单 `order.create` 复制订单头）：那是初始事实的建立，
不是转移；建单前的矛盾闸已走 `assertNoVisaContradiction`。除此之外 `backend/src` 内三列的写入全部经状态机。

### 6.5 写入路径登记（谁调了哪个事件）

| 写入路径 | 事件 / 派生 | 落库 |
|---|---|---|
| `setOrderVisaStatus`（改备注 / 代理自助 / 改单申请 VISA） | `orderVisaDeclarationEvent` → DECLARE_* | `writeOrderVisaStatus` → 任务有无同步 |
| `setPassengerVisaExempt`（改自备签 / 改单申请 VISA_EXEMPT） | DECLARE_SELF_ARRANGED / REVOKE_SELF_ARRANGED | `writePassengerVisaExempt` → 任务有无同步 → `rederiveVisaTaskStatus(touch=[PENDING,IN_PROGRESS])` → 办结派生 |
| `swapPassenger`（换人） | SWAP_PASSENGER；resetVisa | `writePassengerVisaExempt(extra=身份列)`；`resetVisaTaskProgress` |
| 签证台任务级流转（`fulfillment.update`） | 整单 SUBMIT / MARK_DOCS_READY / REVERT | `writePassengerVisaProgress({orderId})` → 办结派生 |
| 签证台按人标记（`batchUpdateVisaPassengerStatus`） | 逐人 `visaProgressEvent` 过守卫 | `writePassengerVisaProgress({passengerIds})` → `rederiveVisaTaskStatus(touch=三档)` → 办结派生 |
| 办结派生（`syncOrderVisaCompletion`） | `deriveOrderVisaStatus` | `writeOrderVisaStatus` |
| 拆单（`executeSplitWithinTx` 9d + 事务外） | SPLIT_MOVE（无写）→ 两侧各自 `rederiveVisaTaskStatus(touch=三档)` → 两侧各自办结派生 | 任务列 / `Order.visaStatus` |

**读侧**：签证台列表 / 统计条 / 护照包 / 提醒的「我方的人」= `ourVisaPassengersWhere`，「未送出」= `ourUnsubmittedVisaPassengersWhere`；
导出「签证状态」列 = 派生态 → 文案；统计条三个数按派生态归桶。

### 6.6 现状互相矛盾的地方（只列出，未修；改动需拍板）

1. **换人不重置进度**：`SWAP_PASSENGER` 只回落 `visaExempt`，`resetVisa` 只把任务回 PENDING，乘客级 `visaSubmissionStatus` 不动 →
   新人挂着旧人的「已送签」，下一次按人标记时任务又被派生回已送签。
2. **任务级 FAILED / CANCELLED 与乘客进度脱钩**：任务标 FAILED 不改乘客进度（乘客仍 CONFIRMED），重派生的 touch 集合永不碰 FAILED，
   于是「乘客已送签 + 任务失败」并存且不会自愈。
3. **`NOT_NEEDED` 与自备签的定价副作用**：0903 口径说「不需要签证 ≠ 自备签」，但录单联动仍把全员 `visaExempt=true` 落库，
   套餐定价按人扣自备签减免——「不需要签证」的单实际上吃到了自备签减免；导出侧为此专门把联动置上的人写回「不需要」。
4. **`HAS_VISA` 的两种来源靠审计区分**：录单手选与派生办结落的是同一列同一值，只能靠最近一条 `AUTO_COMPLETE_VISA` 审计判来源；
   审计 fire-and-forget 写失败时派生办结会被当成手选、永不回退（visa-completion 头注已接受此风险）。
5. **混合单 vs 全员联动靠猜**：`HAS_VISA` + `visaExempt=true` 究竟是联动置上还是逐人手勾，只能用「是否全员」推断
   （全员 → ISSUED，混合 → SELF_ARRANGED）；一张全员自备签又手选已签证的单永远显示「已签证」。
6. **任务有无同步只撤 PENDING**：订单改成不需要 / 全员改自备签之后，IN_PROGRESS / CONFIRMED 的签证任务留着（只给 warning），
   签证台仍看得见一条零乘客的任务，提醒 VISA_MISSING 的范围（在办任务）也仍会圈到它。
7. **订单头 `HAS_VISA` + 乘客 PENDING**：录单手选已签证的单，乘客态派生为 ISSUED、导出写「已签证」，但乘客级进度仍是 PENDING；
   若此后录单人改回 NEEDED，这些人立刻变成「待处理」——同一批人两天内在签证台一出一进。
8. **`orderVisaStatusLabel` 的回落混词汇**：订单级未表态时「签证状态」列回落**任务级**文案（如「处理中」），与同列其它行的**乘客级**文案
   （待处理 / 材料准备 / 已送签）不是一套词。
9. **代理权限不对称（待拍板）**：代理设 `NOT_NEEDED` / `HAS_VISA` 与运营同权否决任务（现状钉死）；改单申请 VISA 类却排除 `HAS_VISA`。
10. **拆单后源单可能剩一条无人任务**：全部非自备签乘客拆走时源单任务不重派生也不撤销（9d 跳过零人侧），签证台上仍挂一条。
