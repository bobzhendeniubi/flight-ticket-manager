# 跨单分房（两张单合住一间房）需求方案

> 状态：设计稿 **v2**（2026-09-14）。v1 三条拍板保留（§十五）；v2 按同日 codex gpt-6-astra 评审重写（评审全文：`docs/反馈存档/2026-09-14-跨单分房方案-astra评审.md`）。
> 范围：**全做**（不走收缩版）。目标读者：产品 / 研发 / 房控。估时见 §十四。

---

## 一、背景与问题

运营的真实目标：**系统里的分房表当真值，房表直接从系统导出，房控不用再靠备注人工分一遍。**

今天做不到，卡在一条边界上：分房表长在每张订单身上（`Order.roomAssignment.roomGroups`），一个「房间盒子」只能装本单的乘客，保存接口拒绝任何不属于本单的归属。于是先进的单和后进的人不能合占一间房；三人间也不是房型问题，本质是「先进的单 + 后进的人合占一间」；导出的房号在导出时临时编，两张单的人永远不会印成同一个房号。

系统里唯一跨单的「同一间房」记号是拆单时自动写的 `splitPairKey`。评审确认：它证明了「跨订单汇总后再取整」可用，**没有**证明「任意共享房恒占一间」。v1 里「房控 / 导出各改一处键」不成立，v2 把三件事彻底分开：**物理房身份、计费份额、住宿行归属**。

## 二、方案（A，修订版）

分房表仍留在各自订单的 JSON 上（编辑器、导出、拆单都读它），但跨单合住的「房间」有自己的真值：一张轻量的共享房表 + 成员表。房控算物理房、导出编房号、锁与版本都以共享房表为准；订单 JSON 里的房组只是每单视图，由服务端派生写入。

不做方案 B（团期房间实体接管全部分房）。

## 三、数据模型

```
SharedRoom 共享房
├─ id                 服务端生成，客户端不能指定
├─ hotelId            真实酒店（占位酒店 / 随机档不允许）
├─ hotelRoomTypeId    房型（容量提示读它）
├─ checkIn / checkOut @db.Date，房内所有成员的订单行入住区间必须与之一致
├─ status             ACTIVE | DISSOLVED
├─ version            Int，每次变更 +1，CAS 用
├─ notes              房控备注（内部）
└─ createdById / createdAt / updatedAt / dissolvedAt / dissolvedReason

SharedRoomMember 成员
├─ sharedRoomId
├─ orderId / orderItemId   归属订单与酒店行（必填）
├─ passengerId             unique(sharedRoomId, passengerId)
└─ roomFraction            Decimal(4,1)，允许 0，0.5 步进；本订单行在这间房的计费份额

SharedRoomRequest 幂等记录
├─ requestToken unique / fingerprint / resultJson / createdAt
```

`Order.roomAssignment.roomGroups[]` 增加 `sharedRoomId`（镜像）。带 `sharedRoomId` 的房组：`orderItemId` 必填、`roomFraction` 允许 0、乘客集合 = 成员表里本单成员。**不写** `OrderItem.metadata.sharedRoomKey`（一条酒店行可能同时有普通房和多个共享房，标量放不下）。

真值优先级：成员表 > 订单 JSON。服务端每次改成员表都同步重写涉及订单的 JSON；提供一致性校验脚本（dry-run 列出不一致的单）。

## 四、三条独立口径

**物理房**：共享房逐晚去重计 1 间。某晚计入的条件：至少一名成员所属订单处于房控有效状态（`COUNTED_STATUSES`）且该成员订单行的入住区间覆盖该晚。与份额无关，与人数无关。普通房组维持现状：一个盒子 1 间（份额 0.5 也算 1 间，不合桶），拆单配对键合桶规则不变。

**计费份额**：每个成员（订单行）在共享房里的 `roomFraction`。保存时硬校验 **Σ份额 = 1**（拍板默认主单 1、其余 0；房控可手改）。行级 `roomsBilled` = 该行普通房组份额 + 该行共享成员份额之和，**显式写 0，不写 null**（null 会重新激活 metadata 兜底）。份额变动不重算金额，降到 0 也提示「计费房数由 X 变为 0，金额不自动重算」。

**归属**：共享成员必须归属真实酒店行（`hotelRoomTypeId` 非空，酒店非占位、非随机档）。首次把一张旧单拉进共享房时，该单**所有**酒店房组必须补齐 `orderItemId`（前端强制选行；后端遇到「部分有归属、部分无归属」直接 400），避免无归属旧组靠酒店名文本碰运气而消失。

## 五、房量闸：变更前后全量比较

现有前瞻闸只收「整间数 + 拼房人数」，表达不了「共享房替换」。新增：

```
assertHotelFitAfterChange(tx, {
  affectedOrderIds,          // 请求订单 ∪ 触及共享房的全部成员订单
  nextSnapshots,             // 这些订单变更后的分房表 + 酒店行 + 成员
  options: { allowNonWorsening }
})
```

- `used_after(酒店, 晚)` = 其余订单现状物理房 + 受影响订单按新快照算的物理房，共享房按 `sharedRoomId` 跨两部分去重。
- `used_before` 用受影响订单的旧快照同法算出；`allowNonWorsening` 按 `used_before` 比较，不再用「排除本单」的残缺基线。
- 所有会改分房、归属、酒店、日期的入口统一走它：跨单保存、单单保存、换酒店、酒店改期、机票改期平移酒店、拆单、取消恢复。录单新增仍用现有 `ProspectiveOccupancy`（录单时不可能已共享）。

## 六、锁与幂等协议

1. 算出受影响订单集合：请求里的订单 ∪ 触及的共享房的所有成员订单（含已取消 / 软删成员，解绑要用）。
2. 按订单 id **升序** 逐个 `SELECT … FOR UPDATE`。
3. 锁后重读订单、乘客、酒店行、成员、版本；集合若扩大，回滚重试（最多 3 次），不许持大 id 锁再补小 id。
4. 按酒店 id 升序、周期 id 升序锁包房周期；酒店无周期时 `pg_advisory_xact_lock(hashtext(hotelId))`。
5. 跑 §五闸；同事务写成员表、订单 JSON、`roomsBilled`、幂等记录、审计。

**现有入口改锁序**：单单分房保存现在是先锁酒店周期再改订单，改成先锁 Order；换酒店、酒店改期、拆单已是订单先，但酒店行读取要挪到锁后复核。

**版本**：请求带 `expectedVersions { sharedRoomId: version }`，不匹配 409「该房间已被他人修改，请刷新」。单单保存改到带共享键的组也要过 CAS。

**幂等**：`requestToken` 唯一；同 token 同指纹回放首次结果，同 token 不同指纹 409；`sharedRoomId` 在首次成功时生成落库，重试复用。

## 七、接口

### `GET /hotel-control/shared-rooms/workbench?hotelId&checkIn&checkOut`（ADMIN / STAFF）

返回该酒店该区间：有效订单列表（单号、状态、代理、酒店行 [行 id、房型、入住退房、roomsBilled]、乘客 [id、中文名、拼音名、性别、当前所在房组或共享房]）、共享房列表（id、房型、version、成员、备注）、普通房组列表。

### `PUT /hotel-control/shared-rooms`（ADMIN / STAFF，代理不开放）

```
body: {
  hotelId, checkIn, checkOut, requestToken,
  expectedVersions: { [sharedRoomId]: number },
  rooms: [{
    sharedRoomId?: string,          // 缺省 = 新建，id 由服务端生成
    hotelRoomTypeId: string,
    notes?: string,
    groups: [{ orderId, orderItemId, passengerIds: string[], roomFraction }]
  }],
  dissolve?: string[]               // 要整间解散的共享房
}
```

语义：成员从旧位置（旧共享房或普通房组）移出；共享房成员清空即 `DISSOLVED`；同一乘客出现两次 400；乘客不属于订单 400；订单行不是真实酒店行 400；订单非有效状态 400；订单行入住区间与共享房不一致 400；Σ份额 ≠ 1 400；人数超房型 `capacity` 只 warning。响应带 warnings 与每张涉及订单的新 `roomsBilled`。

### `PUT /orders/:id/room-assignment`（现有，改）

- 服务端以锁后现状为准保留 `sharedRoomId` 与 `splitPairKey`，**客户端发来的这两个字段一律忽略**（代理可用此端点，不能让客户端造键）。
- 带 `sharedRoomId` 的组：只允许改 `notes`；改乘客、酒店名、房型、份额、归属或删除该组 → 400「该房组与他单合住，请在房控页跨单分房里调整」。
- `roomFraction` 允许 0 仅限带 `sharedRoomId` 的组（服务端判定）。
- 锁序改为先 Order 后酒店；过 §五闸。

## 八、一致性规则：入口矩阵

原则：任何让「同一间房」不再成立的变更，**自动解绑并明示**（拍板 2），不静默。

「解绑」的定义：把该订单行在该共享房的成员删掉，本单对应房组变回普通房组（保留乘客、`orderItemId`）。份额为 0 的：**钱不动**（`roomsBilled` 仍按 0 计），物理按普通房组 1 间计，响应警告「该房组原与他单合住、计费 0 间，解绑后物理占 1 间，金额未重算」。共享房剩余成员不变；清空即 `DISSOLVED`。

| 入口 | 规则 |
|---|---|
| 换酒店 `swapItemHotel` | 该行有共享成员 → 事务内先解绑本单该行全部成员，再用 §五闸判定目标酒店；warnings 按角色文案。含随机档落位、换房型。 |
| 酒店改期 `rescheduleItemHotel` | 同上先解绑再闸。 |
| 机票改期连带平移酒店日期 `rescheduleOrderItem`，批量改班次，纠错平移 | 平移前对全部有共享成员的酒店行解绑；批量结果逐单带警告。 |
| 套餐改档 `changeOrderBundle` | 现有闸禁止已落真实酒店的行改档，共享房只允许真实酒店，正常不可达；加防御：到达即解绑。 |
| 拆单（含 no-show 自动拆、按人改期拆） | 共享成员按人搬：成员的 `orderId / orderItemId` 改到新单新行。份额：整组搬走份额跟走；混合劈时份额默认留源单，`roomSplit` 可指定。目标单没有承载行时建 ¥0 HOTEL 行 `roomsBilled = 搬走份额`（可为 0）承载住宿事实，Σ`roomsBilled` 守恒。拆单闸 15「混合房组先分开」对共享组不再适用。带 `sharedRoomId` 的组不写 `splitPairKey`。 |
| 按房组拆行 `splitHotelItemByRoomGroup` | 共享组允许 0 份额搬行，成本按份额比例（0 份额成本 0）。 |
| 取消 / 退款 / 软删 | 成员保留、状态无效 → 不计物理房；共享房若只剩 0 份额有效成员，物理仍 1 间，房控看板提示「共享房主单已取消」；导出备注标「合住方已取消」（代理导出不带单号）。 |
| 恢复（取消恢复、退款驳回、管理员强制恢复、回收站恢复） | 恢复前校验：共享房 ACTIVE、酒店行日期与共享房一致；通过则按恢复后快照过 §五闸；不一致则解绑 + 警告。回收站恢复只清 `deletedAt`，不自动回有效状态，成员照旧保留。 |
| 换人 / 订正乘客 | Passenger 原地更新，`passengerId` 不变，成员不动；重算性别混合与人数提示。 |
| 改单住 / 拼住、补单房差联动 | 该行有共享成员 → 400「该行与他单合住，请先在跨单分房里解除」。 |
| no-show 航段作废 | 只写航段 metadata，不动住宿，不动成员。 |

## 九、导出

- 三个导出（分房表、整班机、全岗总表）共用一个房间身份映射：`sharedRoomId ?? \`${orderId}:${groupId}\``，作用域 = (`hotelId`，入住日)；酒店名只用于展示。全岗总表现在自己在单内编号，改成同一映射。
- 共享房印同一房号，不因一侧份额 0.5 / 0 印不同后缀。备注列：内部导出写「与 FTM… 合住」，代理导出只写「与他单合住」。
- 约束：同一乘客同一入住区间只能在一个房组 / 共享房（保存时 400），导出每人一行不扩展成乘客 × 住宿段。

## 十、代理侧与对外视图

- 新增 `serializeRoomGroupsFor(role)`：AGENT 只拿 `{ id, roomType, passengerIds(本单), roomFraction, isShared, notes(本单) }`，剥掉 `sharedRoomId`、`splitPairKey`、对方信息；订单详情、列表、代理导出统一走它（现在 `...order` 原样展开，`roomAssignment` 没被脱敏）。
- 换酒店、改期等响应里的 warnings 按角色生成：AGENT 版不含对方单号（拍板 3）。
- 对方单号只在内部视图动态生成，**不写进** `notes`。
- 审计、提醒当前只对 ADMIN / STAFF 开放，不改权限。

## 十一、房控下钻与提醒

- 占房下钻 `getOccupyingOrders` 每张单显示三列：参与共享房数、计费份额、去重物理房；明细注明不可直接相加。
- 提醒规则 8 增加「部分未分房」：有酒店行的订单里仍有乘客不在任何房组 / 共享房。

## 十二、前端

- 房控页新增「跨单分房工作台」：选酒店、入住、退房（默认从销控板带入）→ 左边跨订单乘客池（按订单分组，标当前位置），右边房间盒子（房型、成员来源单、每单份额可改、性别混合与人数超标提示）→ 一次保存；409 时提示刷新。
- 单单分房编辑器 `RoomingEditor`：份额保留 0 与 0.5 与 1（现在除 0.5 外一律归 1）；共享组显示「已与他单合住」标签并锁定（只能改备注）；不再自行构造丢字段的对象，保存只提交可改字段。
- 房控页单单分房入口传 `hotelItems`，新建组必须选归属行。

## 十三、验收反例（测试必须覆盖）

1. 三人合住 1 + 0：房控物理 1 间，两单 `roomsBilled` 分别 1 / 0，导出同一房号。
2. 主单取消，只剩 0 份额成员：物理仍 1 间，看板有提示。
3. 同一单在同酒店同区间有两条酒店行，各自加入不同共享房。
4. 旧单部分归属：跨单保存 400，补齐归属后通过。
5. 混合归属旧单被换酒店：解绑后物理房数与看板一致。
6. 0 份额成员 no-show 自动拆单：成员搬到新单，目标单建 ¥0 行，Σ`roomsBilled` 不变。
7. 并发：跨单保存 vs 单单保存 vs 换酒店 vs 拆单交错执行，无死锁、无覆盖（真库集成测试）。
8. 同 requestToken 重放同结果，改指纹 409；expectedVersions 过期 409。
9. 代理订单详情与代理导出不含 `sharedRoomId`、对方单号；换酒店响应 AGENT 版 warnings 无单号。
10. 拆单房组重存（编辑器）不丢 `splitPairKey`，两个半间仍合成 1 间。
11. 三个导出对同一共享房印同一房号；全岗总表不再自编号。
12. 改单住 / 补房差在共享行被拒。

## 十五、拍板记录

**2026-09-14（v1 三条）**

1. 三人合住计费份额默认：主单 1 间、其余 0；金额不自动重算，差额走改结算价。
2. 改期 / 换酒店 / 改档自动解绑并警告，不拦操作。
3. 代理不露对方单号，只看「已与他单合住」。

**v2 新增口径（默认按此做，不同意请指出）**

4. Σ份额 = 1 硬校验（保存 400），不允许 1 + 0.5 这类合计。
5. 解绑后 0 份额那张单：钱不动（`roomsBilled` 仍 0），物理按普通房组 1 间计，响应警告。
6. 共享行上的改单住 / 拼住、补单房差直接拒绝，先解除合住再改。
7. 共享房只允许真实酒店真实房型，占位酒店 / 随机档待落位不参与。
8. 单单分房端点忽略客户端发来的共享键与拆单配对键，服务端以锁后现状为准。
