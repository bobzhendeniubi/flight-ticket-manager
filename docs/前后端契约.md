# 前后端契约（@ftm/contracts）

## 这东西解决什么问题

改造之前，同一份「请求体长什么样」在三个地方各写一遍：后端 `*.schemas.ts` 的 zod、
admin-web `api.ts` 的手写 interface、sales-web `api.ts` 的另一份手写 interface。
三份各改各的，于是：

- `DocumentType` 前端多一个后端根本不认的 `'OTHER'`；
- `StaffRole` 后端加了 `OPERATIONS`，前端抄本没跟，「岗位」页就是没这个选项；
- `AuditTargetType` 少 `MARKETING`，海报审计行的图标和名称是空的；
- 权限改动只提了后端，前端还是只读，运营报「没有权限」。

现在事实源只有一份：`packages/contracts`。后端 `*.schemas.ts` 只剩一行
`export * from '@ftm/contracts/<module>'`，两个前端 `import type` 同一份定义。

## 包里有什么

| 文件 | 装什么 |
|---|---|
| `src/enums.ts` | 57 个 Prisma 枚举的镜像（**不** import `@prisma/client`） |
| `src/errors.ts` | 错误信封 `ApiErrorBody` + 稳定错误码 + 各码的 `details` 形状 |
| `src/common.ts` | 分页信封 `{ page, pageSize, total }` |
| `src/<module>.ts` | 各模块的请求体 / 查询参数 zod schema 与响应 DTO 类型 |
| `src/lib/*.ts` | 前后端都要用的纯函数：时区换算、业务日、姓名归一、国籍码表、票号校验、凭证 data-URL |

包只依赖 `zod`。**绝不能**依赖 `@prisma/client` —— 那是带 native engine 的服务端包，
进不了浏览器 bundle。

## 加一个新端点：三步

### 1. 先在契约包里定 schema

`packages/contracts/src/<module>.ts`：

```ts
import { z } from 'zod';
import { orderStatusSchema } from './enums.js';

export const markOrderPaidBodySchema = z.object({
  orderId: z.string().min(1).max(64),
  amountCny: z.number().positive().max(100_000_000),
  note: z.string().max(500).optional(),
});
export type MarkOrderPaidBody = z.infer<typeof markOrderPaidBodySchema>;

/** 响应 DTO 用纯 TS type 就行 —— 出参不在后端跑 parse，只做类型。 */
export interface MarkOrderPaidResult {
  orderId: string;
  status: z.infer<typeof orderStatusSchema>;
  paidAmountCny: number;
}
```

模块是新的就再建一个文件，并在 `src/index.ts` 的桶里补一行 `export *`。

### 2. 后端用它

routes 里照旧 `parse`，import 路径不变（`*.schemas.ts` 是个 re-export 壳）：

```ts
import { markOrderPaidBodySchema } from './orders.schemas.js';

app.post('/mark-paid', { preHandler: [...] }, async (req) => {
  const body = markOrderPaidBodySchema.parse(req.body);
  return service.markPaid(body);
});
```

**不要**在 routes 里就地写 `z.object({...})`。守卫测试
（`backend/src/lib/contracts-guard.test.ts`）会红。

### 3. 前端 import，不要手抄

```ts
import type { MarkOrderPaidBody, MarkOrderPaidResult } from '@ftm/contracts';

markOrderPaid: (token: string, body: MarkOrderPaidBody) =>
  apiFetch<MarkOrderPaidResult>('/orders/mark-paid', { method: 'POST', body, token }),
```

## 几条规矩

**枚举改了，先改 `schema.prisma`，再同步 `src/enums.ts`。**
`backend/src/lib/prisma-enum-mirror.test.ts` 逐个枚举对账值集合与值对象，漏同步立刻红。
新增枚举记得在 `PRISMA_ENUM_MIRRORS` 索引表补一行，否则「两侧枚举名对齐」那条会红。

**出参不加 `parse`。** 响应 DTO 只做类型。出参再跑一遍 zod 是白花运行时开销，
而且真有一条数据不合 schema，倒霉的是正在用系统的人，不是写代码的人。

**请求体类型给前端用时注意 `z.input` 与 `z.infer` 的区别。**
schema 里有 `.default()` 或 `z.coerce.date()` 时两者不同：`z.infer`（= 输出）里
defaulted 字段是必填、`coerce.date` 是 `Date`，而前端实际发出去的是「可以不填」和
「字符串」。这类请求体要么在包里额外导出 `z.input<typeof xxx>` 版本，要么前端先别套。

**撞名走子路径。** `bundleItemSchema` 在 `orders` 与 `products` 里各有一份、是两件不同的
东西（录单的套餐行 vs 套餐定义的内容行）。桶文件只放订单那份，产品那份写
`import { bundleItemSchema } from '@ftm/contracts/products'`。

**纯函数 helper 也归这儿。** 前后端都要用同一份口径的东西（时区、姓名归一、票号校验）
放 `src/lib/`，后端原路径留 re-export 壳。判断标准很简单：前端会不会为了这件事自己
再写一份？会，就搬进来。

## 构建链

`tsc -b` 项目引用把顺序管住了：`backend` / `admin-web` / `sales-web` 三个 tsconfig
各有一条指向 `../packages/contracts` 的引用，`npm run build` 会先把契约包编出来。
所以从干净工作区直接 build 任意一端都能过。

- 单独编契约包：`npm run build:contracts`
- CI：三个 job 在 `prisma generate` 之后都加了这一步（vitest 也是从
  `node_modules/@ftm/contracts` 的 `dist` 里加载它）
- Docker：三个 Dockerfile 都先 `COPY packages/contracts/package.json` 再 `npm ci`
  （否则 workspace symlink 建不出来），然后 `COPY packages` + 编契约包，最后编自己。
  backend 的 runner 阶段还要 `COPY /app/packages` —— `node_modules/@ftm/contracts`
  是条 symlink，不带上目标运行时就是 `ERR_MODULE_NOT_FOUND`。

**一个坑**：`git mv` 会保留原文件的 mtime。搬文件进包之后，`tsc -b` 可能认为项目没变而
增量跳过、不出 `dist`，报一堆「Cannot find module」。搬完先 `tsc -b --force` 一次。

## 还没搬的

- **routes 里 19 个文件、56 处内联 `z.object`**，多是一次性小入参
  （`{ disabled: boolean }` 这种）。基线冻在 `contracts-guard.test.ts`，只减不增。
- **响应 DTO 目前只收了公共部分**（分页信封、错误 details）。`serializeOrder` 那类大 DTO
  仍长在 `orders.service.ts` 里，等那份文件拆完再收，免得跟拆分撞车。
- **带 `.default()` / `z.coerce` 的请求体**在前端仍是手写 interface，理由见上面
  `z.input` 那条。
