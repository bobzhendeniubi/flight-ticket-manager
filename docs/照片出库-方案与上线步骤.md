# 照片出库：护照照片 / 收款凭证移出 Postgres —— 方案与上线步骤

> 2026-09-25 · 分支 `worktree-agent-a6d1179bd572e4c7b`（自 main@c31dca68 切出）。
> 本文是内部资料：设计、读写入口盘点、上线 / 回滚 / 环境注意点、待拍板。

## 1. 背景

实测库（2026-09-26 只读查询）1754MB，其中 `Passenger` 表 1503MB —— `passportPhotoUrl` 全是
`data:image/jpeg;base64,…` 内联图：5411 张 / 1438MB / 平均 272KB / 最大 699KB，按内容去重只有 4663 张
（196MB 是同一张图存了多份：拆单、批量、复用）。`Payment.proofUrl` 179 张 54MB，`Receipt.proofUrl` 22 张 6.8MB。

照片每天新增 50-80MB；每日 `pg_dump` 已 1.2GB，本机留 16 份 ≈ 15GB，每天净增约 1GB，约 5 周写满磁盘
（07-02 曾因磁盘满让 Postgres 连续 PANIC 15 次）。

目标：图片**字节**移出 Postgres，存到本地磁盘的内容寻址 blob 存储，库里原列只存短引用。
**对前端的接口契约不变**：前端照旧提交 data URL；今天返回照片的接口照旧返回 data URL。

本次只处理三列：`Passenger.passportPhotoUrl`、`Payment.proofUrl`、`Receipt.proofUrl`。
其它图片类列（`PaymentChannel.qrImageUrl`、`MarketingPoster.imageDataUrl`、`OperationalReminder.attachmentUrl`、
Bundle/Transfer/Visa 的 photo）很小，**不动**。

## 2. 设计

### 2.1 BlobStore（`backend/src/lib/blob-store.ts`）

- 键 = 字节的 sha256（64 位小写 hex）；同一张图存多份天然去重。
- 目录分片 `<BLOB_DIR>/ab/cd/<sha>`（前两段各取 sha 两位 hex），文件无扩展名（mime 在引用里）。
- 原子写：同目录临时文件 `.<sha>.<pid>.<rand>.tmp` → 写满 → fsync → rename；目录 fsync 尽力而为。
- 已存在的 sha 不重写（`put` 返回 `created:false`）。
- **永不删除**：没有 delete 接口，回填脚本也不删；孤儿 blob 只占磁盘。
- 读路径严格校验 sha 格式（`/^[0-9a-f]{64}$/`），路径只由校验过的 hex 拼出 → 不可能目录穿越。
- 抽了 `BlobDriver { put / get / exists }` 接口，只实现 `LocalFsBlobDriver`；将来接阿里云 OSS 再写一个 driver，引用格式不变。
- 根目录 `BLOB_DIR`：容器缺省 `/data/blobs`（Dockerfile 预建并归 ftm 用户，compose 挂命名卷）；本地开发缺省
  `backend/var/blobs`（已 gitignore）；集成测试在 `tests/integration/setup.ts` 指到一次性临时目录。
- `probeBlobDir()`：启动自检（能建 / 能写 / 能读 / 能删），backend 启动日志打 `🗂 图片 blob 目录可写` 或 ERROR。
  不可写**不阻断启动**（写入口会回退内联落库，见 2.5），但要一眼看见。

### 2.2 引用格式（`backend/src/lib/image-ref.ts`）

一列里可能出现三种值，靠前缀互斥、绝不混淆：

| 形态 | 例子 | 说明 |
|---|---|---|
| **blob 引用** | `blob:sha256:9f86d0…（64 hex）;image/jpeg` | 出库后的标准形态。mime 只认魔数嗅探结果（JPEG/PNG/WEBP/GIF），不信客户端申报值 → 同字节必得同引用 |
| 内联 data URL | `data:image/jpeg;base64,…` | 历史形态；前端仍以此提交，写入口统一转成引用；存量由回填脚本转 |
| 外链 | `https://…` | 历史 / 外部来源，保持现状，读取走 `safe-fetch`（SSRF 防线不变） |

浏览器的 `blob:` 对象 URL 长成 `blob:https://host/uuid`，与 `blob:sha256:` 前缀 + 定长 hex 天然区分，`parseBlobRef` 对它返回 null。
生成 / 解析只在这一个模块（`makeBlobRef` / `parseBlobRef` / `isBlobRef`）。

### 2.3 写路径 + 读路径：Prisma 客户端扩展（`backend/src/db/image-blob-extension.ts`）

落这三列的写入口太多（见第 3 节），而且大半是 `order.create` 里的嵌套 `passengers.create`、事务里的
`tx.passenger.update` 这类间接写；逐个改业务入口既漏得掉，也挡不住将来新加的入口。所以卡口放在 Prisma 层：
`db/prisma.ts` 的 `prisma = baseClient.$extends(createImageBlobExtension())`，对**每个**模型操作：

- **写**：`args.data / args.create / args.update`（含嵌套关系写入信封 `create / createMany / update /
  updateMany / upsert / connectOrCreate`，任意深度；`{ set }` 算子）里的 data URL → blob 引用。
  `where / select / include` 一概不碰（CAS 条件里的旧值不能被改写）。
- **读**：结果树里（含 include / select 带出的嵌套关系，任意深度）的 blob 引用 → data URL。
  业务代码与前端契约（接口返回 data URL）完全不变：`serializeOrder`、签证台 `listPassengerPhotos`、
  收款列表、对账台……一行都没改。
- 覆盖面（Prisma 5.22 已实测）：顶层 CRUD、嵌套写、交互式事务里的 `tx.xxx`、批量事务 `$transaction([...])`、
  `createMany` / `upsert`。**不覆盖** `$queryRaw` / `$executeRaw`：raw SQL 看见的是库里的真实引用（仓库里的
  raw 用法只有「列非空即有图」判断和把值原样拷到新行，都不需要还原）。
- 遍历按 DMMF 剪枝：只下钻能通向图片列的关系字段，不碰标量 / Json 列（`gatewayPayload` 里哪怕有同名键也不动）；
  通不到图片列的模型直通零开销。图片列名在全 schema 里唯一，`image-blob-extension.test.ts` 有 DMMF 守卫：
  将来别的模型加了 `proofUrl` 之类的同名列，必须同步登记进 `IMAGE_COLUMNS`，否则测试红。
- 类型：`prisma` 仍标成 `PrismaClient`（`$extends` 后的类型与全站 `client: PrismaClient` 形参不兼容；
  扩展只改查询行为不改模型类型）。另导出 **`rawPrisma`**（不带扩展的原生客户端），只给回填 CLI /
  兜底清扫用——它们要看见真实引用、拿旧值做 CAS。业务代码一律用 `prisma`。
- 开销：写入多一次 base64 解码 + sha256 + 文件写（几 ms）；读多一次文件读（本地 SSD 单张 <1ms，8 路并发）。
  结果树遍历只走关系键，200 单的列表页量级不到 1ms。

### 2.4 要字节的消费方

护照包 zip（`orders/passport-zip.ts`）、按酒店导护照（`hotel-control/hotel-control.passports.ts`）、
签证包（`orders/orders.export-visa-bundle.ts`）三个入口共用 `passport-zip.fetchPhoto` / `extFromUrl`：

- `fetchPhoto` → `lib/image-ref.resolveImageBytes`：blob 引用读本地 blob；data URL 本地解码；
  http(s) 走 `safe-fetch`（SSRF 防线原样保留）。读不到一律 null，调用方记「下载失败」。
- `extFromUrl` 认 blob 引用（按引用里的 mime 给后缀）。
- 因为读钩子已经把值还原成 data URL，这三个入口平时拿到的就是 data URL；`fetchPhoto` 能读引用是为了
  旧值 / 裸客户端 / 钩子还原失败时仍能兜住。

### 2.5 失败口径（宁可多占库、绝不丢图；绝不 500）

| 场景 | 行为 |
|---|---|
| 写入：data URL 解不出 base64 / 字节不是 JPEG·PNG·WEBP·GIF / 超 16MB | **保留内联原值落库** + WARN（`[image-ref]`）。每日兜底清扫会再试，转不了就一直留着 |
| 写入：blob 目录不可写 / 磁盘满 / 卷没挂 | **保留内联原值落库** + ERROR。业务不因存储故障失败；清扫 / 回填随后再转 |
| 读取：引用指向的 blob 缺失 / 读失败 | **保留引用原样返回** + WARN。前端图裂、`hasPassportPhoto` 仍 true、导出 README 记「下载失败」——让「有图但读不到」看得见，而不是伪装成「客人没传」 |
| 导出 / 打包 | 读不到 → 记入缺图明细，照旧出包 |

「有无」判定口径不变：引用非空即有图（`serializePassengerRecord` 的 `hasPassportPhoto`、签证台 SQL
`length("passportPhotoUrl") > 0`、缺照片提醒规则 `passportPhotoUrl IS NULL / ''`、导出「是否有护照图」列）。

### 2.6 存量回填 CLI（`backend/src/tools/backfill-image-blobs.ts` → `dist/tools/backfill-image-blobs.js`）

内核在 `lib/image-blob-backfill.ts`（worker 清扫共用）。

```
node dist/tools/backfill-image-blobs.js                       # dry-run：只统计，不写 blob、不改库
node dist/tools/backfill-image-blobs.js --apply               # 真转
node dist/tools/backfill-image-blobs.js --apply --limit=1000  # 分批：每次最多 1000 行，重复执行即续跑
node dist/tools/backfill-image-blobs.js --apply --table=Payment,Receipt --batch=20
node dist/tools/backfill-image-blobs.js --apply --reverse     # 回滚前：引用 → 内联
```

- 默认 dry-run。按表分批（缺省 50 行），主键 keyset 游标取「仍是 `data:%`」的行；转成功的行不再匹配前缀
  → **幂等、可断点续跑**，中断后直接重跑。
- 每行：解码 → 嗅探 → sha → 写 blob → **读回校验 sha**（对不上立刻停）→ CAS 条件更新
  `UPDATE … WHERE id = ? AND md5(列) = 旧值 md5`（旧值几百 KB，比 md5 省一遍传输）。CAS 0 行 = 期间有人改了 → 跳过，下次再看。
- 转不了的行跳过并点名 id，原值保留。**永不删除 blob**；不动 `updatedAt`（存储搬家不是业务变更）。
- 输出：每表 扫描 / 已转 / 字节 / 新 blob / 去重 / 跳过(转不了) / 跳过(CAS) / 剩余待转；结束提示
  `VACUUM FULL "Passenger", "Payment", "Receipt"`（锁表，低峰手动，工具不执行）。
- 只走 `rawPrisma`。`--apply` 前会先探测 blob 目录可写，不可写拒绝跑。
- `--reverse`：引用 → 规范 data URL（申报 `image/jpg`、夹换行的历史写法会被规范化成 `data:image/jpeg;base64,…`，字节一致）；
  blob 缺失的行跳过并点名。

### 2.7 每日兜底清扫（worker）

`queue.ts` 的 `image-blob-sweep` 队列，每 24h 一次，`worker.ts` 调 `backfillImageBlobs({ apply: true, limit: IMAGE_BLOB_SWEEP_LIMIT })`
（缺省 200 行，`0` = 关）。只捞漏网行：blob 目录当时不可写而回退内联的、raw SQL 写进来的。
存量回填不靠它——但要知道：**部署后它每天也会默默转 200 行**，不希望它动存量就在 `.env` 里设 `IMAGE_BLOB_SWEEP_LIMIT=0`。

### 2.8 基础设施

- `backend/Dockerfile`：`mkdir -p /data/blobs && chown -R ftm:ftm /data`，`ENV BLOB_DIR=/data/blobs`。
  预建目录是为了 Docker 首次挂**空**命名卷时沿用镜像里挂载点的属主（ftm uid 1001）——否则卷是 root 的，写入会一直回退内联。
- `docker-compose.prod.yml`：backend + worker 都挂 `blob_data:/data/blobs`，`BLOB_DIR=/data/blobs`；worker 多一个
  `IMAGE_BLOB_SWEEP_LIMIT=${IMAGE_BLOB_SWEEP_LIMIT:-200}`。命名卷按 compose 项目名隔离：实测 `ftm_blob_data`、测试
  `ftm-staging_blob_data`，与 `postgres_data` 同一套隔离机制，不会串。`down -v` 会连它一起删。
- `infra/staging/backup-blobs.sh`：`rsync -a`（**不带 --delete**）卷 → `/opt/ftm/backups/blobs`，排除 `*.tmp` / `.probe.*`。
  crontab 每天 03:40（排在 03:30 的 `backup-db.sh` 之后）：
  `( crontab -l 2>/dev/null; echo "40 3 * * * bash /opt/ftm/infra/staging/backup-blobs.sh >> /opt/ftm/backups/backup-blobs.log 2>&1" ) | crontab -`
  **从此「库备份 + blob 备份」才是一套完整备份**，pg_dump 里不再有照片。恢复见脚本末尾注释。
- `infra/refresh-staging-db.sh`：灌完库后把实测卷 rsync 到测试卷（只增不删，对实测只读）；卷不存在时警告不中止。
- 没动：`infra/staging/backup-db.sh`、`watchdog.sh`、`infra/local/`。

3. **分批 apply**：`--apply --limit=1000` 跑几轮（每轮几分钟，业务不受影响：每行独立 CAS，期间被改的行下轮再转），
   看日志有没有「转不了」/「CAS 冲突」；最后 `--apply` 收尾到 `剩余待转` 只剩转不了的行。
4. **核对计数 + 抽样比对**（同 4.1 第 3 步；抽样用 `ftm_blob_data`）。
5. **低峰 `VACUUM FULL`**（会锁表几分钟到十几分钟；先确认当天备份已完成）：
   `docker exec ftm-postgres-prod psql -U ftm -d ftm -c 'VACUUM FULL "Passenger", "Payment", "Receipt";'`
   之后 `select pg_size_pretty(pg_total_relation_size('"Passenger"'))` 应从 1.5GB 掉到几十 MB。
6. **看备份体积**：次日 `ls -lh /opt/ftm/backups/ftm_*.sql.gz` 应从 1.2GB 掉到 ~100MB 量级。
7. **装 blob 备份 crontab**（2.8）；跑一次 `bash /opt/ftm/infra/staging/backup-blobs.sh` 看文件数 ≈ 去重后的图数。
8. 之后再 `refresh-staging-db.sh` 时脚本会自动同步 blob 到测试卷。

## 5. 回滚

**旧代码读不懂 blob 引用**：旧的 `fetchImageSafely` 把 `blob:sha256:…` 当非 https 外链 → null（导出记「下载失败」）；
后台 `<img src="blob:sha256:…">` 裂图；`hasPhoto` 仍 true。所以：

- 只想回滚本批之外的东西：正常回滚即可，本批不受影响。
- 要回滚**本批代码本身**：先把库转回旧代码读得懂的形态，再切代码：
  1. 先关清扫：`.env.prod` 设 `IMAGE_BLOB_SWEEP_LIMIT=0`，重启 worker（否则它每天还会转 200 行）。
  2. `docker exec ftm-backend-prod node dist/tools/backfill-image-blobs.js --apply --reverse`（同样分批 / 幂等；
     要求 `ftm_blob_data` 卷还在——blob 永不删，所以一定在；blob 缺失的行会点名，说明卷被人动过，先从
     `/opt/ftm/backups/blobs` 恢复再跑）。
  3. `剩余待转` 为 0 后再 `git checkout <旧 commit> && deploy`。
  4. 反向会把库撑回原来大小；旧代码上线后新图又内联进库。
- 反向不是常规操作，只在本批要整体撤回时用。

## 6. 测试环境与本地的注意点

- **本地开发**：`BLOB_DIR` 缺省 `backend/var/blobs`（gitignore）。`npm run dev` 启动日志同样打 `🗂`。
  想清空本地图就删这个目录（本地库里的引用会读不到 → 裂图 + WARN，不 500）。
- **单测**不依赖 blob 目录（自建临时目录 / 注入 store）；**集成测试** `tests/integration/setup.ts` 把 `BLOB_DIR`
  指到 `mkdtemp`，与库一样一次性。同一进程内多个集成文件共用这一个临时目录（内容寻址、永不删除），断言「新 blob /
  去重」计数要用每次独有的字节（回填集成测试就是这么写的）。
- **测试站**：卷 `ftm-staging_blob_data`；`down -v` 会把它删掉 → 库里引用全部裂图，重跑 `refresh-staging-db.sh`
  同步即可。`refresh-staging-db.sh` 在两套都用新 compose 起过之前会警告「卷缺失、未同步」。
- **恢复演练**要两样一起：`gunzip -c ftm_*.sql.gz | psql …` + `rsync -a /opt/ftm/backups/blobs/ <卷 mountpoint>/`
  （再 `chown -R 1001:1001`）。
- **磁盘**：blob 目录只增不减（去重后每天几十 MB）；15GB 的历史 pg_dump 里仍含照片，按既有 14 天轮转自然消失。
- `git status` 里 `backend/var/` 永远不该出现（已 gitignore）。

## 7. 需拍板 / 未做

- **VACUUM FULL 时间窗**：锁三张表几分钟到十几分钟，选低峰；不跑的话库文件不缩小（但 dump 已经变小，因为 dump 不含死元组）。
- **每日清扫默认开（200 行/天）**：部署后即使不跑回填，它也会慢慢转存量。要「只有人工回填才动存量」就设 `IMAGE_BLOB_SWEEP_LIMIT=0`。
- **blob 缺失的展示口径**：现在是「保留引用、图裂、hasPhoto 仍 true」（宁可暴露故障也不伪装成没传）。若更想显示成「未上传」，改 `materializeImageValue` 一处即可。
- **备份出岛**：blob 目录与 pg_dump 一样只在本机；接 OSS 时新写一个 `BlobDriver` 即可（引用格式不变），存量目录 rsync 上去。
- **转不了的历史行**：CLI 会点名 id（按实测数据形态预计为 0；`payments` 集成测试里那种 `SGVsbG8=` 假图只在测试库有）。
- 其它图片列（收款码 / 海报 / 提醒附件 / 产品图）本次不处理。
- 没动导出 / 列表类查询的 `omit: { passportPhotoUrl }`（另一批在做，与本批互不冲突：omit 掉的列钩子看不见，自然不还原）。
