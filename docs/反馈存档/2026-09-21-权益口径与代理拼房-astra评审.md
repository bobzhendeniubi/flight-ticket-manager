其余重点证伪结论：

- **次数状态集正确。**`PAID/PROCESSING/TICKETED/COMPLETED/CHANGE_REQUESTED/CHANGED` 与决议一致，待支付、退款申请中、终态及独立占位单不进入 `pendingPaidTripCount`。退款驳回到 PROCESSING 后重新计入，符合口径。这里按订单状态判断，并非额外核验收款流水。
- **两张已付未飞单贡献两次额度。**可以分别核销 1 次；兑换两次各需 5 次的权益仍需余额至少 10。没有“每单只能核销一次”的约束，但决议也没有要求。
- **挂单证件匹配**使用类型＋号码，trim/大小写归一，并通过 `resolveDocPairs` 解析完整合并链；不依赖拼音姓名。新漏洞在自动冲正的另一套别名查询。
- **负数余额会拒绝新的正数核销。**核销先走详情重算，再在 Serializable 事务中复核净额；但订单变化与事务外快照重算之间的竞态仍未消除，不能称为全链路实时一致。
- **自动冲正幂等的金额约束成立。**`reversalOfId` 唯一约束配合 `skipDuplicates`，与人工冲正竞争时，已存在的补偿行已完成退款次数，不属于吞掉必要金额写入。现有测试只是预设竞争结果，未验证真实 PostgreSQL 交错。
- **重复取消及取消→恢复→再取消**不会再次冲正同一原记录；恢复后新写的核销可以在再次取消时冲正。no-show 仅首次调用，回程作废 job 不重复调用。TIMEOUT/FAILED 通常无候选，多两次查询；强制流转等情况下仍有兜底价值。
- **拆单 A→B→C 已确认漏追 A。**这是决议明确接受的“一跳”边界，不算擅自改变口径，但不能宣称多次拆单已覆盖。另有恢复提示缺口：B 触发的补偿仍挂 A，恢复 B 时按 `orderId=B` 计数会漏提示。建议后续按触发单保存关联或生成明确人工待办。
- **代理权限主路径没有发现范围绕过。**缺档案/停用在认证及路由拒绝；候选确实叠加代理范围，房型反查不取消过滤。正常保存与运营加成员共同锁订单，锁集合扩大重试，未发现该交错下的越权写入。`expectedVersions` 单独附带只读房 ID 会被忽略，不会返回 403，也不会修改该房。
- **`lockScope` 是 UI 限制。**直接 API 可选其他酒店/日期，但仍校验订单归属、住宿行酒店和区间，符合你给定的后端口径。递归 CTE 使用 `UNION ALL`，脏环存在不终止风险，属于既有 helper 问题，并非绕过成无限权限。
- **迁移为增量结构变更**，保留旧核销的空 `orderId`；旧客户端省略挂单字段仍可用。新列初始 0 不会多给额度。导出与档案确实调用同一计算函数，但快照新鲜度不同仍会造成显示差异。
- 未检出四端源码中的禁用内部同事姓名。
