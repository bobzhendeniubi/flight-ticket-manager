**1. [CRITICAL] 先解绑再读取 before，把本次新增占房伪装成“存量超卖”**

证据：`orders.service.ts:14915` 先执行解绑，`:14968` 才调用库存闸；`shared-room-unbind.ts:101、134` 已删除成员并改写 JSON。`hotel-control.service.ts:1641、1663` 从此时数据库计算 before，再允许“不恶化”。

反例：酒店只有 1 间，A/B 共享；B 换成**同酒店另一房型**。解绑后变成共享房 1 间＋B 普通房 1 间。闸看到 before=2、after=2，允许提交，实际操作前只有 1 间。酒店改期在旧新区间重叠的夜晚也有同样问题，见 `orders.service.ts:15662、15697`。

修法：解绑先生成变更计划，保留真正旧快照；按旧、新共享成员及 JSON 算完库存，再统一落库。

**2. [CRITICAL] 机票平移及恢复仍没有完整接入 §五闸**

证据：

- `orders.service.ts:10609` 对刚解绑的酒店行仅做 `Math.max(1, roomsBilled)`，`:10621` 仍走旧前瞻。
- `:5754、5762` 取消恢复也按行计费数前瞻。
- `:8530` 管理员强制恢复只做一致性解绑；`:8547` 酒店容量检查只限 `REFUND_REQUESTED → PROCESSING`。

反例：同一酒店行承载两个不同共享房的零份额组，机票平移解绑后应占 **2 间**，前瞻却只加 **1 间**，可放行超卖。全部成员取消、房量被别人占走后，强制恢复有效状态也缺少对应酒店容量闸。

相反，取消恢复主单时，仍有效的零份额伙伴已经让共享房计 1；旧前瞻又加主单的 1，可能把无需新增物理房的恢复拒掉。

修法：所有恢复和平移入口统一提交完整 after 快照；不能用“每行至少一间”代替“每个普通房组一间”。

**3. [CRITICAL] 已解散房和跨日期旧房仍可被保存，产生幽灵共享房**

证据：`hotel-control.shared-rooms.ts:483` 校验版本和酒店，却不校验已有房的 ACTIVE 状态及日期；`:729` 更新不修改状态或日期。`:721` 解散也没有递增版本。聚合端 `hotel-control.service.ts:1046、1066` 只计 ACTIVE 房的表内日期。

两条可达反例：

- 解散 S 后，旧版本请求再次更新 S：成员和共享 JSON 能重新写入，S 却仍是 DISSOLVED。JSON 普通聚合跳过它，共享聚合也跳过它，**实际住宿计成 0**。
- 请求拿旧日期的 S，换成同酒店新日期的合法订单行：验证成员日期符合请求，但 S 日期保持旧值。前瞻按请求日期通过，落库后的房控却仍按旧日期计。

修法：锁内强制校验 ACTIVE＋酒店＋完整住宿区间；禁止 `rooms` 与 `dissolve` 重叠；解散及全部成员变更都递增版本。

**4. [CRITICAL] 普通房组本地 id 跨单合桶，三种口径叠加仍能少算**

证据：`hotel-control.service.ts:769` 普通桶键是 `box:${id}`，没有 orderId；`:970、1000` 跨订单累加后取整。

已用原函数复现：

| 同酒店同晚的住宿 | 应计 |
|---|---:|
| A/B 两个普通组，均叫 `local`，各 0.5 | 2 |
| 一对拆单半间 | 1 |
| 一个共享房 | 1 |
| **合计** | **4，实际返回 3** |

这是 main 已有、当前三口径组合仍未消除的漏洞。普通组 id 可由单单接口提交，不能假定跨单唯一。

导出还有对应风险：`room-identity.ts:45` 直接信任 splitPairKey；`orders.service.ts:23928` 房组配对键实际是“本地 groupId＋token”，并非注释声称的全局源行键。拆单 token 按源单作用域幂等（`:18123`），两张不同源单复用同 token、同本地组 id，就会被三个导出合号，库存也会合桶。

修法：普通桶加入 orderId；拆单配对身份由服务端生成并绑定真实拆分来源，不能仅拼本地组 id。

**5. [HIGH] 显式 0 仍会被 null 化或恢复成 1**

证据与后果：

- `orders.routes.ts:1584` 清空全部酒店行 `roomsBilled=null`，`:1602` 跳过 `rooms<=0`。共享组**只改备注**也会把行级 0 写成 null。
- `hotel-control.shared-rooms.ts:373` 的 `readBillingFraction` 将普通组 0 读为 1。解绑保留 0 后，再参与工作台保存会被改成 1；整间解散时也会发生，因为 `:620` 生成普通零份额组后进入同一回写流程。
- `orders.routes.ts:1509` 又拒绝普通零份额组，导致合法解绑结果无法原样重存。

原函数内存复现得到：解绑普通组 `{roomFraction:0}` 的计费读取结果为 **1**。

修法：显式 0 在所有计费读取和写入中保留；物理一间与计费零间分别计算。为合法解绑的零份额普通组保留服务端来源标识及重存资格。

**6. [HIGH] 共享保存的成员集合未闭合，Σ 校验与实际回写不一致**

证据：`hotel-control.shared-rooms.ts:546` 用 Map 覆盖同一 `(orderId, orderItemId)` 的份额；`:649` 却逐输入 group 建 JSON，`:785` 又逐 group 累加计费。

同一房内，同一订单行提交两个不同乘客组，各填 1：校验只看到最后一个 1，实际行级回写却是 2，还生成重复 group id。schema 没有禁止这种输入。

另一个问题是 `:468` 仅收集请求显式列出的旧共享房。把乘客从 S1 拖进新 S2、请求不列 S1 时，`:588` 会从 S1 的 JSON 移走乘客，却不会删除 S1 成员表记录。乘客同时存在于两间共享房，旧房不能正确清空，物理数和镜像分叉。

修法：先规范化每房每订单行唯一分组；按乘客查出全部旧关系，加入锁集合、版本校验及迁出计划，再从同一规范化结果写成员、JSON、计费数。

**7. [HIGH] 拆单 4b 只打通了“整个零份额本地组搬走”，混合共享组仍错误**

证据：

- `orders.service.ts:17854` 仍拒绝含多人的 0／0.5 共享组，前面的共享组豁免没有覆盖这道闸。
- `:18752` 混合共享组仍调用普通 `splitMixedRoomGroup`；`:23930` 强制分半并写 splitPairKey。
- `:18725` 成员迁移只改 orderId/orderItemId，不改 roomFraction，也不递增 SharedRoom.version。

反例：A 的两位乘客在 S 内共同承担份额 1，拆走一人。JSON 变成两侧各 0.5，但两条成员仍各记录 1；按新的订单行去重后成员份额合计变成 2。行级 Σ 断言（`:19249`）仍可能通过，因为它不检查成员表。

此外，解绑只删除 sharedRoomId（`shared-room-unbind.ts:43`），错误生成的 splitPairKey 会留下，再次把已解绑的两个普通半组拼回一间。

no-show 和按人改期确实调用相同拆单内核，见 `orders.service.ts:21012、19681`；**接到内核不等于混合零份额场景能通过**。按房组拆行也只部分放开：`:15333` 仍拒绝源行总份额为 0。

修法：共享组使用独立拆分计划，同时更新成员份额、两侧 JSON、行级份额和版本；默认混合拆份额留源单，禁止生成拆单配对键。

**8. [HIGH] ¥0 承载行会被财务报表计出额外酒店成本**

证据：`orders.service.ts:18702` 复制原 quantity，`:18705` 将成本写为 **null**，不是 0。`finances.service.ts:541` 遇到 null 成本会回退酒店价，`:553` 累加“住宿成本 × quantity”。

因此承载行虽然 amount=0，仍可增加财务汇总酒店成本；毛利明细则会因 null 将订单成本标成未知，见 `finances.service.ts:987、1000`。`sharedRoomCarrier` 目前只有写入点，没有财务消费端识别。

未发现该行直接增加拆单应收或开票人数：金额聚合使用 amount（`orders.service.ts:18803`），开票守恒使用乘客数（`:19134`）。不能把这个成本漏洞扩大成已证实的重复收费或退款漏洞。

修法：承载行显式写零成本，并验证报表、毛利明细及后续成本重算均保持其零成本语义。

**9. [HIGH] 锁集合扩大时原事务补锁，可直接形成死锁；SharedRoom 锁协议也未落实**

证据：`hotel-control.shared-rooms.ts:350` 在同一事务循环补锁，`:363` 没有回滚，`:365` 重试耗尽还直接返回。

确定的成环：S 原有 A、B；请求甲只保留 A，请求乙只保留 B。甲先锁 A，乙先锁 B；重读成员后甲等 B、乙等 A。重新排序循环不会释放已经持有的锁。

保存在 `:478` 普通读取 SharedRoom，到酒店闸后的 `:729` 才通过 UPDATE 隐式锁行；解绑则在 `shared-room-unbind.ts:89` 显式先锁 SharedRoom。单单入口先 Order 的改动正确（`orders.routes.ts:1469`），但整个协议并未统一。酒店无周期时也没有规格要求的 advisory lock，见 `hotel-control.service.ts:1433`。

修法：事务外收集候选关系；锁后扩大则抛出专用重试信号、整事务重开；稳定后按 SharedRoom id 升序锁行，再锁酒店。禁止重试耗尽继续提交。

**10. [HIGH] 换酒店、酒店改期继续使用锁前住宿行，仍可错判酒店和错算差价**

证据：`orders.service.ts:14570、15553` 在事务外读取 item；锁内 `:14863、15629` 只重读订单，没有重读 item。酒店改期的房控 hotelId 在 `:15605` 锁前确定；差价在 `:15602` 锁前计算。

并发例：改期读取酒店 H1 后等待 Order 锁；另一请求先把该行换到 H2。改期取得锁后仍检查 H1 库存，却最终修改已属于 H2 的行日期，H2 新区间未经校验。期间共享保存改变 roomsBilled，也会令代理差价使用旧份额。

修法：取得 Order 锁后重新校验行归属，并以锁后行重算酒店、日期、份额、价格及成本。当前修复只重读解绑后的 JSON，没有解决原评审指出的 item 快照问题。

**11. [HIGH] 单单保存给每家酒店传入整单酒店行，前瞻会跨酒店重复计数**

证据：`orders.routes.ts:1545` 将全部 hotelItems 放进同一个 nextOrderItems；`:1554` 按酒店循环时仍传同一份。`assertHotelFitAfterChange` 在 `hotel-control.service.ts:1629` 直接接纳这些行，不再过滤 hotelId。

反例：一单在 H1/H2 同晚各有一个已归属普通组，每家容量 1。只改备注时，对 H1 的 after 会连 H2 的组一起计成 2，形成误拒。

新下钻列也有同类范围错误：`hotel-control.service.ts:2842` 统计整单普通组，没有按本酒店、本晚过滤；无分房表则回落 0。三列虽然已添加，`physicalRoomsDeduped` 仍不能代表该查询范围的真实参与物理数。

修法：逐酒店生成限定后的快照；下钻复用同酒店、同晚的聚合函数。

**12. [MEDIUM] 幂等正常异常清理已修，但并发及崩溃窗口仍不完整**

证据：`hotel-control.shared-rooms.ts:415` 在事务外 create 占位；`:428` 同 token 处理中返回 409，并建议换 token；`:444` 清理失败被吞掉；`:844` 业务事务内才写结果。

已解决：普通业务异常后删除占位；成功结果与业务变更同事务提交，顺序重放可用。

未解决：进程在占位后崩溃会永久留下 pending；同 token 并发不会等待首次结果。提示换 token 还可能让尚未结束的首次请求与新请求同时执行。

修法：将唯一占位和业务结果纳入同事务；或实现明确的处理状态、租约及恢复机制。同 token 处理中应提示重试同 token，不应建议换号。

**13. [MEDIUM] 审计不是同事务，before 还可能已被原地修改**

修法：独立复制不可变 before；逐单审计与成员、JSON、roomsBilled、幂等结果一起提交。
