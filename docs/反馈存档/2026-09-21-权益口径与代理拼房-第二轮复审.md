## 二、A–G 证伪结果

### A. F1「仍有有效订单承载行程」判定（读真实函数 + 内存反例）

`findCarriedOrderIdsByDoc`（`traveler-benefits.auto-reverse.ts:424-506`）把「承载」定义为 (a) 任何谱系外已付未飞且未 no-show 的单，或 (b) 拆单谱系一跳内（源单 / 候选挂的单拆出去的目标单）的单哪怕已飞。反例结果（`ce5.mts`）：

| 场景 | 结果 | 判定 |
|---|---|---|
| A1 直挂 A、没拆过单；客人另有无关未飞单 D；取消 A | **不补回**，仅 INFO 审计 `carriedByOrderIds=[D]` | **错**：A 上的升舱没享受到，5 次白扣 |
| A1b 同上，A 去程 no-show | 不补回 | 错，同上 |
| A2 A→B→C，P 在 C 已飞，取消 A | **补回 5** | 错（一跳边界，白拿） |
| A2b A→B→C，P 在 C 未飞，取消 A | 不补回（靠 (a) 兜住） | 对，但只是 (a) 的副作用 |
| A3 一跳 A→B，B 已飞，取消 A | 不补回 | 对（第一轮原始反例已挡） |
| A4 A no-show，P 只在 A；历史已飞单 H、B 上无 P | 补回 | 对 |
| A5 谱系外别单 D2 已起飞 1h / D3 未飞但已打 no-show 标 | 补回 | 对 |

- **反向漏冲不是「保守」，是双扣路径**：A1 后核销行仍挂 A（orderId=A），规则 12 对 D 那一程只看挂 D 的行与 `orderId==null` 存量行（F3 修法），挂 A 的行被排除 → D 起飞后照常生成「次数升级待核销」→ 运营再扣 5 次。客人两次行程共扣 10 次只享受 1 次升舱。而规则 13 不会喊（`computeAvailableTrips({tripCount:6, pendingPaid:1, redeemed:5}) = 2 ≥ 0`），INFO 审计是唯一痕迹，`AuditLogsPage` 默认不按 INFO 筛，且档案页不展示审计。
- **时间口径**：已飞判定用 `flightSchedule.departureTime > at`（UTC 瞬时比较），与聚合的 `departed`（`traveler-profiles.aggregate.ts:340`）同一口径，`departureTz` 只影响展示不影响这里，无时区坑；no-show 用 `hasNoShowMark`（`metadata.noShow != null`），与飞行次数口径同源。触发单靠 `id: { not: orderId }` 排除，事务内状态未写回也不影响。
- **INFO 审计够不够运营发现**：不够（见上）。跳过时至少该建一条待办或把严重度提到 WARNING。

### C. F5 规则 13 现算成本 / `_min` / rebuildInFlight

- **查询数（读代码数的）**：`groupBy`(1) + 快照 `findMany by id`(1) + 档案表全量最小行(1) + `computeCombinedTripCounts` 内部 `order.findMany`(1) + `loadLegacyTripCounts` 的 `legacyTicket.findMany`(1) = **5 条固定**，不随 N 增长；内存侧 `buildTravelerAggregates` 遍历这 N 个档案的全部有效订单。N = 有正净核销的档案数，功能未上线时为 0，上线后按核销量线性增长，内部量级可接受。
- `_min` 口径：`ensureFresh`（`traveler-profiles.service.ts:907-923`）与 `bootstrapTripCountProfilesIfEmpty`（`orders.export-trip-stats.ts:247-257`）都 `where: { mergedIntoId: null }` + `_min`。指针行排除正确：`doRebuildAll` 只 upsert 聚合命中的 canonical 行、update 带台账的 preserved 行、deleteMany 其余 canonical 行（`:750-760`），指针行永远不刷、必须排除；迁移 `UPDATE … SET refreshedAt='2000-01-01'` 打的是全表，排除指针行后 `_min` 才能在重建后前进。**首访重建保证成立**：部署后先开某一人详情只刷那一行，`_min` 仍是 2000 → 列表 / 导出下一次访问必触发重建。
- rebuildInFlight：`travelers.routes.ts:32` 的 service 是模块级单例，列表路径去重有效；但 `orders.export-trip-stats.ts:268` 每次 `new TravelerProfilesService().rebuildAll()`，实例私有的 `rebuildInFlight` 不与路由实例共享 → 导出与列表可并发跑两份全量重建（既有问题，`_min` 让触发频率更规律）。另：重建中途抛错（如 upsert 撞大小写变体）时 `_min` 永远不前进 → 每次列表访问都再起一次后台重建（N6）。
