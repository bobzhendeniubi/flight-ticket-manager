## 新发现

以下区分修复回归与修复遗漏，不把旧问题换名当作新修复成果。

### N1 · CRITICAL：新建共享房被酒店过滤整间漏计【回归】

**证据：** `hotel-control.shared-rooms.ts:944、1018` 给新房预生成 `sharedRoomId`，却没传 `hotelId`；`hotel-control.service.ts:1592、1610` 对有 ID 的覆盖项查询数据库归属，查不到即过滤。新房此时尚未落库。

**反例：** 容量 1，原 A/B 共享一房；保存为“旧房留 A＋新房住 B”。前瞻只算旧房 1，提交后实际为 2。JSON 中的新共享组又被普通聚合跳过，不能补回漏计。

原函数复现：相同新房覆盖项，不带 hotelId 返回 **`[0]`**，带正确 hotelId 返回 **`[1]`**。

**修法：** 所有新房覆盖项显式携带已验证的 hotelId；区分“待创建”与“数据库归属异常”，后者应报错，不能静默漏计。

### N2 · CRITICAL：多行两阶段解绑会把已经解绑的共享键写回来【回归】

**证据：** `shared-room-unbind.ts:217、233` 每份计划都从同一份原订单 JSON 构造**整单快照**，`:275` 整份覆盖写回。平移先生成全部计划，再逐份应用（`orders.service.ts:10712、10862`）；恢复同样如此（`:5840`）。

**反例：** 一单 I1/R1、I2/R2：

- 计划一删除 I1 的共享键。
- 计划二仍保留原始 I1/R1，只删除 I2 的共享键。
- 顺序应用后，I1/R1 被写回，但其成员记录已经删除。

原函数已复现这一最终状态。平移后 I1 新日期的住宿会被 JSON 共享键跳过，又没有成员表占用承接，后续房控少算。

**修法：** 按订单合成一份最终 JSON；按 SharedRoom 合成最终成员集合；库存闸与落库共同消费这份计划。不能逐行覆盖整单快照。

### N3 · CRITICAL：恢复的两套库存闸分别通过，合计却超限【回归】

**证据：** `orders.service.ts:5772、5798` 新闸只拿共享 touched 行；`:5854、5864` 普通行排除 touched 后另走旧闸。两次检查时订单都还是取消态；最终 `via:'restore'` 又跳过恢复后的容量复检（`:8665`）。

**反例：** 同晚容量 1、容忍 0，取消单恢复后需要共享房 1＋普通房 1。两道闸分别看到需求 1，都通过，最终需求 2。配置正容忍值时，也能以相同方式突破**累计**缺口上限。

恢复快照还有两处遗漏：

- `shared-room-unbind.ts:330、337` 按乘客成员行生成状态，没有按 SharedRoom 去重；同组两名乘客会生成两个相同覆盖项。`hotel-control.service.ts:1638` 逐项加一，原函数复现同一房被算成 **2 间**。
- `orders.service.ts:5830` 丢弃新闸返回的容忍超售明细；`:5864、6059` 返回／审计里的 `hotelOversold` 只有旧闸结果。

**修法：** 每家酒店一次提交本单全部恢复后住宿行；共享状态按房 ID 唯一化；统一计算累计缺口并收集审计明细。

### N4 · CRITICAL／HIGH：恢复仍可并发超卖，多房解绑仍可死锁【遗漏】

**容量互斥遗漏：** `orders.service.ts:8666、9185` 强制恢复读最终物理余量，但没有取得酒店库存锁；`hotel-control.service.ts:1166、1175` 是普通查询。

两张不同的纯酒店取消单同时强制恢复，各自在事务内看到“自己占 1、对方仍取消”，容量 1 时可同时提交。Order 锁不能让不同订单互斥。

**多房锁顺序遗漏：** `shared-room-unbind.ts:168` 只对**本行**房 ID 排序；平移按数据库未排序的酒店行逐次调用（`orders.service.ts:10683、10712`）。A 先锁 R1 再 R2，B 先锁 R2 再 R1，仍可成环。逐酒店循环也没有统一酒店排序（`:10780`）。

**修法：** 事务级收集全部资源，统一按 Order→SharedRoom→酒店顺序及各自 ID 排序加锁；强制恢复同样先取库存锁再读取最终状态。补双订单、双共享房的屏障测试。

### N5 · HIGH：隐式迁出清掉留守方 JSON 和计费份额【回归】

**证据：** `hotel-control.shared-rooms.ts:633` 把隐式房加入 touched；`:875` 删除这些房的全部旧组。后续只重建显式 dissolve 和 rooms（`:898、946`），没有重建隐式房留守组；成员表却保留留守方（`:1087`）。`:1186` 又把失去组引用的行写成 0。

**反例：** S 有 A、B，B 原份额 0.5；只把 A 拖进新房且请求不列 S。B 的成员记录仍在，JSON 组消失，`roomsBilled` 被清成 0。

另一个并发遗漏：隐式房查询发生在 Order 锁之前（`:623`），锁后只复查**已发现房间**的成员（`:411`）。等待期间乘客被别的请求放入新房，该新关系不会被发现和清理。

**修法：** 从最终成员集合重建隐式房的留守镜像；锁后重新发现乘客所属房间，房集合扩大也必须整事务重试。

### N6 · HIGH：共享拆组计划没有接管行级拆分【回归／遗漏】

**证据：** `orders.service.ts:18913` 先按普通行策略落库，`:19015` 才生成共享组计划。`split-move-strategies.ts:391、543` 的 HOTEL/BUNDLE 行策略并不了解共享组。

原函数复现：

- 两人共享组份额 1，自动拆走一人：行级为 **0.5／0.5**，共享 JSON／成员计划却是 **1／0**；行 metadata 仍写配对键。
- 一行承载两个混合共享组，行级 `roomSplit=0.5` 被逐组重复使用（`orders.service.ts:19012`），两个组共搬 **1**，行只搬 **0.5**。

`orders.service.ts:19695` 只核两单行级总和，无法发现每侧行与成员／JSON 不一致。整组迁移 `:19132` 也没进入只针对混合组的版本更新 `:19200`。

**修法：** 先形成整单房组分配计划，再按归属行汇总份额、生成行搬移。行级 roomSplit 必须在多个组之间分配；断言每侧每行与成员／JSON 相等；全部成员迁移都更新房版本。

### N7 · HIGH：新增拆单核验把不同拆分的订单集合合并，原碰撞仍通过【修复无效】

**证据：** `room-identity.ts:121` 按 token 合并所有拆单记录的 source/target，`:140` 只检查订单是否属于这个并集，没有检查是否属于**同一条拆单记录**。

原函数复现：A→B、C→D 使用同 token，四单同键 `local:token`，核验仍返回可信。三个导出仍会错误合号。

库存端仍直接按该键合桶。若两个独立拆分各只剩一侧有效，两个无关 0.5 组会合成 1 间。

**修法：** 配对身份绑定真实拆分来源及源组；核验按单条拆分关系进行。库存与导出必须使用同一可信身份，不能只给导出加检查。

### N8 · HIGH：锁后检查漏掉单价，代理差价仍可用旧值【遗漏】

**证据：** `orders.service.ts:15011、15891` 用锁前 `item.unitPrice` 算换酒店／改期差价；`:15140、15953` 的锁后字段列表没有单价。现有改结算价入口可在酒店、日期、份额不变时更新单价（`:7399`）。

**反例：** 代理改期先读旧价，运营改结算价先提交；代理取得锁后所有比较字段相同，仍按旧价计新增晚数差价。

**修法：** 锁后重算报价；或将单价、数量、成本及其他报价依赖纳入完整版本校验，变化即 409。

### N9 · HIGH：新增迁移脚本可覆盖并发业务修改【回归】

**证据：** `backend/scripts/rewrite-shared-room-group-ids.ts:84` 全量读快照，`:128` 按 id 无条件覆盖整份 roomAssignment，没有事务内重读或 CAS。写入还只保留 `{roomGroups}`，丢失其他顶层字段。

脚本读取后若工作台完成分房、解绑或备注修改，脚本会把旧 JSON 写回来；成员表、roomsBilled 却保持新值。

**修法：** 每单事务加锁后重读，只替换当前命中的 id，保留其他字段；逐单审计同事务提交。该脚本不能充当跨单分房的业务回滚方案。

### N10 · MEDIUM：pending 回收没有占位所有权保护【部分修复】

**证据：** `hotel-control.shared-rooms.ts:531` 删除条件只有 token＋id，没有“仍为 pending”；`:1250` 完成结果按 token 写；`:567` 异常清理也只按 token 删除。

超时请求恰在回收读取之后完成，成功记录仍可被删除；旧请求迟到的写入／清理也可能作用于重新创建的占位。

**修法：** 回收用 pending 状态和时间条件做 CAS；返回 reservation id，完成写入、异常清理均绑定该 id，并确保过期执行者不能提交业务结果。

### N11 · MEDIUM：三个导出的“确定性编号”仍不一致【回归】

**证据：**

- `orders.export-room-allocation.ts:673、678`、`orders.export.ts:293` 跨日期汇总时 scope 只有酒店；`orders.export-master.ts:510` 却包含入住日。同酒店不同入住日的编号规则不一致。
- `room-identity.ts:197` 对同一身份保留首次遇见的排序键。拆单两侧订单号不同，交换遍历顺序仍会改变排序。原函数已复现房号 **1／2 对调**。

**修法：** 三导出统一酒店＋入住日作用域；同一身份取稳定的规范排序键，例如所有候选键的最小值。

### N12 · MEDIUM：保留显式 0 时，把旧普通组的 null 也变成 0【兼容回归】

**证据：** `hotel-control.shared-rooms.ts:454` 先做 `Number(g.roomFraction)`；`Number(null)===0`。原来的正数判断会把普通 null 回落为 1，现在回写成 0。

原函数复现：`null／0／省略` 分别得到 **`0／0／1`**。

**修法：** 转数字前先区分 nullish 与显式数值；普通组 null／省略仍按既有缺省 1，显式 0 才保留。
