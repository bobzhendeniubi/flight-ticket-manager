# 二、新发现

## C1 · CRITICAL：解绑留下的「0 份额普通组」在老式前瞻闸里按 0 间算，落库按 1 间算 → 真超卖

**证据链（四段代码互相矛盾）：**

1. 解绑保留原份额、不改 `roomsBilled`：`shared-room-unbind.ts:113-119`（`stripSharedRoomId` 只剥
   `sharedRoomId`/`splitPairKey`，`roomFraction: 0` 原样留下）、`:378-379`（「不改 roomsBilled（钱不动）」）。
   0 份额那一侧正是方案 §十五拍板 1 的**默认形态**（主单 1、其余 0），不是边角数据。
2. 房控物理口径把它当 1 间：`hotel-control.service.ts:748-752` `groupRoomFraction` 对 `n <= 0` 一律
   兜底成 1；`:792-806` 按桶 ceil → 1 间。销控板/余量因此显示 1 间（这是**正确**的，§八 明文
   「物理按普通房组 1 间计」）。
3. 老式前瞻闸把它当 0 间：`orders.service.ts:26239-26248` `toProspectiveOccupancy(0, …)` →
   `{ wholeRooms: 0, solos: [] }`（`Math.max(0, Math.ceil(0)) === 0`）。取值来源
   `orders.service.ts:15083`（换酒店 `item.roomsBilled ?? 1`）、`:15995`（酒店改期）、
   `:25917`（stays 闸 `row.roomsBilled ?? 1`）——注意 `null` 会兜底成 1，**只有显式 0 会塌成 0**，
   而「显式写 0 不写 null」正是方案 §四 的硬要求。
4. 这四条路在「该行已经没有共享成员」时就走老式闸，不走 §五闸：
   - 换酒店：`orders.service.ts:15366-15381`（`else if (needsHotelFitCheck)` 分支）
   - 酒店改期：`:16160-16180`
   - 恢复：`:5889-5918`（`gatedHotelIdSet` 只认「有共享成员」的酒店）
   - 机票改期连带平移：`:10937-10954`（`ungatedShifted`）

**反例（全程合法操作，无并发）：**
B 单是共享房 S 的 0 份额成员（`roomsBilled = 0`）。
① 运营给 B 换酒店 → 走 §五闸（正确，目标酒店算 1 间）→ 解绑落库，B 留下 `roomFraction: 0` 的普通组、`roomsBilled` 仍是 0。
② 第二天运营再给 B 换一次酒店（或改期 / 取消后恢复 / 机票改期平移日期）→ 此时 `planUnbind` 返回空，
`hasSharedMembers = false` → 走老式闸 → prospective 0 间 → **目标酒店哪怕一间不剩也放行** →
落库后销控板如实显示多占 1 间。同一张单可以反复触发，缺口累加。

**为什么是 CRITICAL：** 这不是并发窗口，是确定性的口径错位；触发者是这个功能的默认份额分配 +
最常见的售后动作；错的方向是**少算**（超卖真实房量），且销控板事后才看得见。

**修法（建议）：** 别再让 `roomsBilled` 当物理前瞻的输入。最小改动是把这四处的
「有共享成员才走 §五闸」改成「**该行在订单 JSON 里有归属房组就走 §五闸**」
（§五闸本来就是按 JSON 算物理，天然吃 0 份额 → 1 间）；退一步的兜底是
`toProspectiveOccupancy` 之前用 `assignedRoomsForItem(order.roomAssignment, item.id, hotelName)`
取 max，绝不让「显式 0」变成「0 间物理需求」。

## H1 · HIGH：隐式迁出后旧共享房 Σ份额可以是 0——一间真房没人计费，不报错也不 warning

**证据：** `hotel-control.shared-rooms.ts:885-890` 的 `Σ份额 = 1` 硬校验**只对 `body.rooms` 里的房间**
生效；隐式触及的旧房（`:662-674` 发现、`:1036-1060` 重建留守镜像）原样保留留守成员的份额
（`:1054 roomFraction: entry.fraction`），从不重算、也不校验；`warnings` 数组在整个函数里只被
容量提示写入（`:891-895`），这条没有任何提示。

**反例（就是仓库自己的集成用例）：**
`hotel-control.shared-rooms.integration.test.ts:1884-1984`——S = A(1) + B(0)；请求只把 A 拉进新房 T、
不提 S。结果断言（:1959-1984）：S 仍 ACTIVE、只剩 B、B 的 `roomFraction` 保持 0、
`bItemAfter.roomsBilled === 0`。也就是说落库后：

- 物理：S 计 1 间（`hotel-control.service.ts:1091-1101`，B 的单有效）+ T 计 1 间 = 2 间；
- 计费：A 在 T 上 1 间，B 在 S 上 **0 间** → Σ roomsBilled = 1。

一间真实房间挂在 B 名下、B 一分钱房费不计，系统从头到尾不吭声。这条用例把这个行为断言成了
「正确」，所以不会有人发现。

对称的另一半也不对：如果前端老老实实把 S 一起列进 `body.rooms`（多数工作台实现会这么做），
那 Σ = 0 ≠ 1 → `:888` 直接 400「计费份额合计须为 1，当前为 0」，运营只是想把一个人拖出去，
却收到一句看不懂的报错，也没有可操作的出路。两条分支都不对。

**修法：** 隐式迁出后（以及解散后）对受影响房间做一次份额收口决策并**明示**，二选一：
(a) 剩余成员里份额最大的一位补到 1（与 §八「解绑」的「钱不动 + 警告」口径对齐，返回
`该房间原计费方已迁出，剩余 X 单计费 0 间，物理仍占 1 间，金额未重算`）；
(b) 保持 0 但必须进 `warnings` 且进审计，让房控看得见「这间房没人付钱」。
无论选哪条，把这条口径写进 §四/§八 并改掉上面那条把缺陷断言成正确的测试。

## M1 · MEDIUM：`computeSharedRoomPhysicalAfterChange` 不按 sharedRoomId 去重覆盖项 → 同一间房被算两次（误拒）

**证据：** `hotel-control.service.ts:1703-1705` 对 `scopedOverrides` 逐条 `add()`，没有按
`sharedRoomId` 去重。而恢复路径的覆盖项是**逐行**拼出来的：`orders.service.ts:5845-5862`
（`kept` 来自 `shared-room-unbind.ts:587-596`，对每个 item 各 push 一条）。
astra N3 的修复只解决了「同一 item 内多名乘客生成多条」（`shared-room-unbind.ts:419-431` 按房去重），
**跨 item 没去重**：同一张单两条酒店行同时挂在同一间共享房（§三 未禁止，反例 3 正是一单两行
各自入房），恢复时这间房会被喂两条覆盖项 → 物理算成 2 间 → `allowNonWorsening` 下
after > before → 本该放行的恢复被误拒（或吃掉一份超售容忍额度）。

**修法：** 在 `computeSharedRoomPhysicalAfterChange` 里按 `sharedRoomId` 做最后一道去重
（同 id 多条时合并 `activeMemberOrderIds`、断言 checkIn/checkOut 一致，不一致就抛错）。
这是聚合器自己的不变量，不该指望每个调用方各自记得去重。

## M2 · MEDIUM：`splitHotelItemByRoomGroup` 把共享成员改指到新行，却不涨 `SharedRoom.version`（绕过 CAS）

**证据：** `orders.service.ts:15802-15808` 只 `sharedRoomMember.updateMany({ orderItemId: created.id })`，
没有 `sharedRoom.update({ version: { increment: 1 } })`。对比拆单里 N6 明确补上的两处
（`:19408-19413`：「成员份额或成员归属变了，version 必须跟着涨」）——同一条不变量，这里漏了。

**后果：** 工作台先打开（拿到 version=V），运营在订单页按房组拆行（成员 orderItemId 变了、version 仍是 V），
工作台再保存 → `expectedVersions` 对得上 → 按**旧** `orderItemId` 重建成员（`:1275-1287`），
把拆行结果悄悄改回去，`roomsBilled` 也跟着按旧归属回写。

**修法：** 该分支补 `version: { increment: 1 }`，并补一条断言。

## M3 · MEDIUM：`PUT /orders/:id/room-assignment` 没有「同一乘客只能在一个房组」校验（§九 明文要求）

**证据：** `orders.routes.ts:1479-1562` 的 reconcile 循环只做「共享组只许改 notes」和
「共享组不许删」，通篇没有 `seenPassengerIds` 之类的去重（对比工作台端
`hotel-control.shared-rooms.ts:864-872` 有）。方案 §九 最后一条写的是
「同一乘客同一入住区间只能在一个房组 / 共享房（保存时 400）」。

**后果：** 客户端把某位乘客同时留在锁定的共享组里、又塞进一个新普通组，
`roomsBilled` 按组累加（`orders.routes.ts:1634-1645`）→ 该行计费凭空 +1；
物理侧共享 1 间 + 普通 1 间 = 2 间（多算 → 误拒别人）。代理也能调这个端点。

**修法：** reconcile 之后、写库之前加一次全量乘客去重（含共享组镜像里的乘客），重复即 400。

## M4 · MEDIUM：拆单 3c 会静默覆盖运营显式填的 `roomSplit`

**证据：** `orders.service.ts:19150-19152` 对「本行有任一共享组被触及」的行无条件
`roomSplitByItem.set(itemId, totalMovedFraction)`，而 `totalMovedFraction` 只汇总**共享组**的份额
（`:19123-19149`）。同一条酒店行上若还挂着普通房组（§三 允许「一条酒店行同时有普通房和多个共享房」），
运营为那个普通组填的 `roomSplit`（例如 0.5）会被整条替换成共享组的合计（常见是 0）。

**后果：** 计费份额守恒仍成立（源行 NONE、不扣减），但「谁付这半间」被系统悄悄改了，
且运营的显式输入被吞掉、没有任何提示。

**修法：** 要么只在「本行全部房组都是共享组」时覆盖，要么 fail-closed 拒绝
（同 `:19116-19121` 那条「一行两个混合共享组」的处理），不要静默改运营的输入。

## M5 · MEDIUM：`lockHotelInventoryForUpdate` 是死代码，方案 §六步骤 4 的 advisory-lock 兜底实际未上线

**证据：** `hotel-control.service.ts:1495-1518` 定义 + `hotel-control.service.test.ts:1968-2035` 单测，

**修法：** 要么接线（`assertRestoreHotelCapacity` 用它替掉两次 `lockHotelBlockPeriodsWithinTx`），

## M6 · MEDIUM：工作台「listed 决定最终成员」语义可静默剔除 0 份额同房成员

**证据：** `hotel-control.shared-rooms.ts:761-773` 记录了这个选择，落库
`:1259 deleteMany({ sharedRoomId })` + `:1275-1287` 只按本次 `room.groups` 重建。
客户端提交一间既有房时若漏掉某个 0 份额成员的 group，该成员会被删除成员表、
JSON 组也不会重建（kept 过滤器 `:943-953` 已经丢掉它），`roomsBilled` 显式写 0（`:1319-1328`），
Σ = 1 校验仍然通过（因为漏掉的恰好是 0）——全程不报错、不 warning，该乘客变成「未分房」。

**修法：** 保存时对既有房做一次「落库现状成员 − 本次 listed 成员」的差集，非空就进 warnings
（甚至要求客户端显式声明移除），不要让「没传」等于「删掉」。

# 三、对第 3 点的独立判断：`assertHotelFitAfterChange` 对「查到但酒店不符」保留静默过滤，是否可接受

**结论：可接受（安全方向正确），但给出的理由是错的，注释必须改。**

三条独立论证：

1. **不可能因此少算。** 被静默过滤掉的覆盖项，其房间按 DB 归属属于**别家**酒店；而本次
   gate 的存量查询 `hotel-control.service.ts:1686-1694` 本来就 `where: { hotelId, status:'ACTIVE' }`，
   别家酒店的房间根本不在 `liveRows` 里。丢弃覆盖项 ⇒ 这间房在本酒店记 0 间 —— 这正是正确答案。
   `overrideIds`（:1680-1684）是从**过滤后**的 `scopedOverrides` 建的，所以被过滤的覆盖项也不会
   顺手把某个 live 行「屏蔽」掉。两个方向都不会造成漏计。反过来，如果按 astra 建议改成抛错，
   错误的方向是「误拒合法操作」，比现在更差。
2. **「换酒店场景依赖」这个理由不成立。** 我逐个查了生产调用方：`swapItemHotel`
   （`orders.service.ts:15348-15356`）在**跨酒店**时显式传 `[]`，同酒店换房型时房间必然属于本酒店；
   `rescheduleItemHotel`（`:16139-16146`）注释明写「改期不换酒店，房间所属酒店恒等于
   roomType.hotelId」；机票平移（`:10917-10924`）与恢复（`:5845-5862`）都已按酒店分组。
   **没有任何生产路径真的依赖这条静默过滤** —— 依赖它的只有 `hotel-control.shared-room.test.ts:311-336`
   那条「调用方允许把两家酒店的覆盖项混着传」的单测。也就是说，现在是「为了一条测试保留一条
   宽松分支」，而 `:1670-1675` 的注释把它说成了生产依赖，属于事实错误。
3. **真正该改的是可观测性，不是严格性。** 建议：保留过滤（别改成抛错，那会把 tolerant 的
   调用契约变成 breaking），但 ①把注释改成事实（「目前无生产调用方依赖，保留是为调用契约宽松」）；
   ②过滤掉覆盖项时打一条 WARN 日志（带 sharedRoomId / 期望 hotelId / 实际 hotelId），
   让「调用方喂错酒店」这种真 bug 在日志里留痕，而不是完全静默；
   ③顺手修掉 L3 那条已经过时的反向注释。

# 四、测试是否真的碰到关键路径

**整体：这一批的测试质量明显高于平均线——真库集成为主，不是拿 mock 糊过去。** 但有三处要指出。

**真的碰到了：**
- 三个集成文件全部走真 Postgres（`vitest.integration.config.ts` + `prisma migrate deploy`），
  本轮实跑 64 个用例全绿，覆盖 §十三 反例 1/3/4/6/7(简化)/8/10/11/12 与 N1–N6 的反例。
- `assertHotelFitAfterChange` 的单测**有**把 `sharedRoom.findMany` 喂上桩
  （`hotel-control.shared-room.test.ts:248-265` 的 `fakeTx`），所以共享房分支是真被执行的，
  不存在「delegate 缺失 → 恒返回 0 → 断言恒真」的假绿。
- N4 的并发反例是两张真单并发强制恢复（f6a666f 附带），不是碰第三方单。
- N1 的修复有**间接硬证据**：末位 commit `4ec5e8d` 被迫把包房从 1 改成 2，说明闸真的开始把
  新建共享房算进去了；同一 commit 把 N5 的 `it.fails` 转回 `it`，说明缺陷确实被修掉。

**问题：**
1. **并发用例没有屏障（astra 的老意见仍然成立）。**
   `hotel-control.shared-rooms.integration.test.ts:524-626`、`:459-523` 用的是
   `Promise.allSettled([reqA, reqB])`，两个请求谁先抢到 Order 锁完全靠运行时调度。
   断言「恰好一个成功一个 409」在当前实现下是稳的（CAS 保证），但它证明不了
   「交错在某个特定窗口」的行为——真正想钉的「锁集合扩大重试」「隐式房锁后再发现」
   （`hotel-control.shared-rooms.ts:692-704`）这两条分支，没有任何测试能确定性地走到。
   建议用 advisory lock 或 `pg_sleep` 注入点造确定性交错。
2. **测试把缺陷断言成了正确（最值得警惕的一处）。**
   `hotel-control.shared-rooms.integration.test.ts:1981-1984` 明确断言
   `bItemAfter.roomsBilled === 0` 且注释写「与 JSON 组的 roomFraction 口径一致，不是被清空」。
   这正是 H1 —— 一间真房无人计费的状态被写进了回归基线。**修 H1 时必须同时改这条断言**，
   否则修复会被测试挡回来。
3. **C1 完全没有测试覆盖。** 「0 份额普通组 → 第二次换酒店/改期/恢复」这条链在
   `orders.shared-rooms-w2.integration.test.ts` 里没有用例（那里的换酒店/改期用例都是
   「解绑那一次」，没有人跑第二次）。这也解释了为什么 astra 两轮都没发现它。
   修复时必须补：解绑后 → 再换酒店到一个只剩 0 间的酒店 → 必须被拒。
4. 次要：`saveSharedRooms` 的审计现已同事务（`:1363`），但集成文件顶部仍留着
   `flushFireAndForgetAudit()`（:128-140）与多处 `afterEach` 调用——注释与实现已经不符，
   属于噪音，建议清掉以免误导。
