> 审查对象：`feat/shared-rooms@4ec5e8d`（相对 `main@63dcf96` 103 commit）。Opus，只读，未改文件、未跑构建。
> 范围：astra B 路 11 条 + N1–N9 复核、代理出口重核、前端三组件、三导出、提醒状态机、文案。
> 钱与库存路径（A 路）不在本路范围，只在与泄露/前端耦合处顺带说明。

## 总体判断：**需先修**（1 条 HIGH 必修，3 条 MEDIUM 建议同批修）

astra B 路的 11 条 + N1–N9 **全部关闭**，代理出口逐个重核**没有发现任何一条能拿到 `sharedRoomId` / `splitPairKey` / 对方单号 / 对方乘客的路径**，文案零人名。这一路的原始目标达成了。

但本轮新发现一条**阻断日常分房**的回归：单单分房端点新加的「普通房组必须提供 hotelName 与 roomType」硬校验，把「房型选填」这个既有 UI 契约打成 400。分房编辑器的房型输入框写着「选填」，仓库里大量存量房组的 `roomType` 就是空串——上线后运营/代理只要不填房型就保存不了分房，且三闸（单测/集成/build）全都覆盖不到（所有用例都填了房型）。这条不修不能上。

**必修项：**

- **H1** 普通房组 `roomType` 空串被硬拒——恢复成允许空串（或前端改成必填，二选一，不能一边写「选填」一边后端拒）。

**建议同批修（MEDIUM）：**

- **M1** 单单端点没有房组 id / 乘客去重，重复提交同一个共享组 id 会让 `roomsBilled` 翻倍。
- **M2** 代理外部 DTO 不带 `orderItemId`，多酒店行订单代理重存分房会丢归属、需要盲选，可能改挂错行。
- **M3** 「三个导出同一房号」只在三份导出的**订单集合相同**时成立；未归属旧房组在全岗总表落的是另一套 scope；全岗总表还会给零乘客房组占号。

**部署前必做：** `ROOM_REMINDER_STATE_MACHINE_SINCE` 必须在 `.env.prod` / `.env.staging` 显式设成部署当日（见 M4），否则闸失效或反向关掉既有「未分房」提醒。

## 三、新发现

### H1 · HIGH — 普通房组 `roomType` 空串被硬拒，「房型选填」的正常分房保存一律 400

**证据**
- `backend/src/modules/orders/orders.routes.ts:1546-1548`
  ```ts
  if (!g.hotelName || !g.roomType) {
    throw new BadRequestError('普通房组必须提供 hotelName 与 roomType');
  }
  ```
- 同文件 `:1383-1384` 把 zod 从必填放宽成 `optional()`（为了放行锁定共享组的省略字段），这条硬校验是补回来的，但**把空串一起拒了**——`main@63dcf96` 的 zod 是 `hotelName: z.string()` / `roomType: z.string()`，空串一直合法。
- 前端从未要求填房型：`admin-web/src/components/RoomingEditor.tsx:752` 的输入框 placeholder 就是「房型（**选填**，如 大床房 / 双床房）」，保存时 `roomType: b.roomType.trim()`（`:498`）可以是 `''`，`handleSave` 里也没有任何房型校验。
- 空房型是仓库里的常态数据形状，随手可见：`orders.export-master.test.ts:663`、`orders.export-room-allocation.test.ts:1395`、`room-group-placement.test.ts:107/114/170` 等大量 fixture 都是 `roomType: ''`。
- **三闸盖不住**：`orders.room-assignment.routes.test.ts` 的每个用例都填了 `roomType: '双床'`（`:106`、`234`、`383`、`564-565`…），没有一条覆盖空房型。

**影响**：部署当天，运营/代理在录单后的「需要分房吗？」、订单页分房弹窗、房控页「订单分房（拖拽）」三个入口，只要有一个房间没填房型（缺省行为），整次保存 400。这是日常主路径。

**修法（二选一，倾向前者）**
1. 把条件收成「只拒 `undefined`，不拒空串」：`if (g.hotelName === undefined || g.roomType === undefined) …`，并保留 zod 层对普通组的语义（或干脆判 `typeof g.hotelName !== 'string'`）。
2. 若坚持房型必填，前端 placeholder 改「必填」并在 `handleSave` 里先拦。

无论哪种，补一条「普通组 `roomType: ''` 保存 → 200」的路由用例。

### M1 · MEDIUM — 单单端点不去重房组 id / 乘客，重复提交同一共享组 → `roomsBilled` 翻倍

**证据**：`backend/src/modules/orders/orders.routes.ts:1481-1521`——`for (const g of body.roomGroups)` 逐条按 `oldById.get(g.id)` 查旧组，命中共享组就 `finalGroups.push({...old, notes})`。body 里出现两条同 `id` 的组，就会 push 两份同一个共享组；`:1636-1645` 的 `roomsByItem` 按 `orderItemId` **累加** `roomFraction`，于是该行 `roomsBilled` 从 1 变成 2，而物理去重按 `sharedRoomId` 仍是 1 间——计费口径与物理口径当场分叉。同一处也没有「同一乘客只能出现在一个房组」的校验，与 `docs/跨单分房-需求方案.md` §九「同一乘客同一入住区间只能在一个房组 / 共享房（保存时 400）」不一致。

（跨单端点那边是有的：`hotel-control.shared-rooms.ts:829-833` 拒重复 `(orderId, orderItemId)`、`:868-871` 拒重复乘客。单单端点缺这一层。）

**影响**：正常前端不会造出重复 id，但 AGENT 能对自家单直接调这个端点；房控间数/结算口径被污染后很难回溯。

**修法**：在 reconcile 之前加两条闸——`body.roomGroups` 的 `id` 去重（重复即 400）、`passengerIds` 跨组去重（重复即 400）。

### M2 · MEDIUM — 代理外部 DTO 不带 `orderItemId`，多酒店行订单的代理重存分房会丢归属

**证据**
- `backend/src/modules/orders/room-group-dto.ts:23-34` 的 `ExternalRoomGroup` 不含 `orderItemId`（这是刻意的，B4 也据此放宽了锁定组的比较）。
- 但这只对**锁定的共享组**做了兜底（`orders.routes.ts:1504-1506` 省略即不比较，`:1516-1517` 落库用 `...old` 保住归属）。**普通组没有这层兜底**：`orders.routes.ts:1549-1552` 落库用的是客户端发来的 `{...g}`，`orderItemId` 没传就是真没有。
- 前端侧：`RoomingEditor.tsx:488-493`，代理拿到的普通组 `b.orderItemId` 恒为 `null`；`hotelItems.length === 1` 时会自动归属到唯一那条行（安全），但 `>= 2` 时 `showItemSelect` 为真，`:450-457` 会拦下保存要求「请为每个房间选择归属酒店行」——代理看到的是**空白下拉**，原归属信息在 DTO 里已经被抹掉，只能凭印象重选。

**影响**：多酒店行订单（拆单、连住两段、套餐+加订酒店）由代理重存一次分房，归属就可能被改挂到另一条行上，`roomsBilled` 随之记错行；房控按行看的数就不准了。`main` 上代理拿的是未脱敏的 `roomAssignment`，归属能原样回传——这是本分支引入的回归。

**修法**：`ExternalRoomGroup` 加回 `orderItemId`（它是**本单自己的行 id**，不含任何跨单信息，泄露面为零），或在普通组分支也按 `old` 兜底补回归属。

### M3 · MEDIUM — 「三个导出印同一房号」的成立条件比承诺窄

三条各自独立，合并成一条报：

1. **订单集合不同 → 房号仍不同（结构性）**。`buildIdentityNumberMap` 是在**本次导出自己捞到的那批订单**上建映射的（`orders.export-room-allocation.ts:682-691`、`orders.export.ts:298-307`、`orders.export-master.ts:920-928`）。三个导出的选单条件根本不同：分房表按入住日区间、整班机按 `scheduleId`、全岗总表按下单时间/代理/渠道筛（代理视角还只有自家单）。同一 scope 里少了一批单，后面的号就整体前移。唯一的跨导出断言 `room-identity.test.ts:271` 只验证了「同一批 entries 换遍历顺序结果一致」，没验证也无法验证「不同订单集合」。**建议**：文档/操作手册明确「跨导出房号一致的前提是同一批订单都在导出范围内」，别让房控按「两份表房号必然对上」来核对。
2. **未归属旧房组在全岗总表落的是另一套 scope**。`orders.export-master.ts:506-518` 的 `roomGroupScope` 只认 `group.orderItemId` 对上的行；没有归属时 `hotelId = null`、`checkIn = ''`，走 `pending:<hotelName>|` 分支；而分房表/整班机用的是 `correlateItem` 回落出来的**真实** `hotelId + 入住日`（`orders.export-room-allocation.ts:661-663`、`orders.export.ts:278-280`）。文件注释已承认这一点，但它意味着存量未归属房组在三表里永远对不上号。共享房因为 `orderItemId` 必填，不受影响。
3. **全岗总表会给零乘客房组占号**。`orders.export-master.ts:921-926` 遍历 `parseRoomGroups(order.roomAssignment)` 的**全部**房组建 identity 条目，包括 `passengerIds: []` 的空组（这种形状在仓库 fixture 里是存在的，如 `orders.export-room-allocation.test.ts:1395`）；另两个导出是**逐乘客**收集的（`orders.export-room-allocation.ts:658-673`、`orders.export.ts:274-290`），空组根本不进映射。同一 scope 里只要有一个排序靠前的空组，全岗总表的号就整体比另两表大 1。**修法**：master 预扫描时过滤 `g.passengerIds?.length > 0`。
