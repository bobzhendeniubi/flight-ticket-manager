## 二、A–F 证伪结果

### A. 新承载判定（读真函数 + 内存反例 ce6.mts）

**where 形状与查询次数（读代码算）**，一次取消 / no-show 事务内 auto-reverse 的固定开销：
1. `orderSplitRecord.findMany({ where: { targetOrderId } })` ×1（:168-175，找直接源单）；
2. `travelerBenefitRedemption.findMany` ×1（候选）；
3. `travelerProfile.findMany()` **全表** ×1（`loadCandidateDocs` :407-412，F2 引入，既有）；
4. `passenger.findMany({ where: { orderId } })` ×1（仅当有源单候选）；
5. 闭包 `orderSplitRecord.findMany({ where: { OR: [{sourceOrderId:{in:frontier}}, {targetOrderId:{in:frontier}}] } })` ×(深度+1)，上限 16（:455-462）——**没拆过单也会发 1 次**（首跳 frontier=[触发单] 返回空），末跳恒空转一次；
6. `order.findMany({ where: { id: { in: 谱系 }, deletedAt: null, status: { notIn: EXCLUDED }, passengers: { some: OR 证件 } } })` ×1，**谱系为空时不发**（:524）；
7. 冲正：createMany + findMany 各 1，每行审计 1 + 待办 findUnique/create 各 1。
两条拆单链典型 = 8~9 条查询，与订单数无关（除 3 的全表档案读，内部量级可接受）。

### D. N7 共享 resolver 与补拉循环

- `loadTripCountMap` 与 travelers 都调 `traveler-profile-alias.ts` 的 `resolveMasterRef`（seen 集合防环、断链停当前行）。export 侧 `byId` 是「命中行 + 逐跳补拉的主档案」的局部 map，但补拉循环跑到「没有新的 wanted」才停，所以链上可达的每一行都在 map 里 → 与 service 全表 map 解析结果一致（唯一差异是断链：两边都停在当前行）。
