# 三、新发现

## N1 · HIGH — C1 只修了四个入口，同构的另外两条前瞻闸原样漏着（方向仍是超卖）

**机理与 C1 完全同源**：`assertHotelStaysFitWithinTx` 把 `roomsBilled ?? 1` 喂给
`toProspectiveOccupancy`（`orders.service.ts:25989`），显式 0 译成 0 间；而
`excludeOrderId` 会把本单**真实占的那 1 间**从基线里整单摘掉
（`hotel-control.service.ts:1389` 的 `id: { not: excludeOrderId }`，基线用的是分房表口径，
`groupRoomFraction` 对 `n<=0` 兜底成 1 间）。摘掉 1 间、加回 0 间 = 净少算 1 间。

**两个未接的调用点**（都是「excludeOrderId 排本单 + 把同单其余行原样加回去」的写法）：

- `orders.service.ts:14649`（`setPassengerSingleRoom` 改单住/拼住，闸在 `:14658`）
- `orders.service.ts:17140`（`addRoomSupplement` 补收单房差，闸在 `:17149`）

两处都写成 `roomsBilled: it.roomsBilled == null ? null : Number(it.roomsBilled.toString())`
——`null` 有 `?? 1` 兜底，**只有显式 0 会塌成 0 间**，正是解绑留下的那一种。

**两处的既有共享房闸挡不住它**：`:14568` / `:17093` 的 `hasSharedRoomMembers` 只拒「该套餐行
**还有活跃共享成员**」，而 C1 场景里成员早就解绑了（这正是 C1 的前提），闸不触发。

**反例**：一张单有两条同酒店同区间的占房行（套餐行 + 补录的酒店行，§三 允许、A 报告 M1 的
反例就是「一单两行各自入房」）。其中一条曾是共享房的 0 份额方、后来解绑 → `roomsBilled = 0`
且分房表里仍有该行的 0 份额普通组。此时对另一条行做「改单住」或「补收单房差」抬房：
基线摘掉 2 间（真实占用），前瞻只加回 1 + 0 = 1 间 → 酒店已满也会被判为「还剩 1 间」放行。
（归并键是 `hotelId|首夜|末夜`，所以需要两行区间相同才会真超卖；区间不同时只是漏检、不新增占用。）

**修法**：与 C1 四处完全一致，套一层已有 helper 即可（需要先取一次 `order.roomAssignment`）：
`roomsBilled: floorZeroRoomsBilledByAssignedRooms(<原表达式>, roomAssignment, it.id, null)`。
补一条「同单两行同酒店同区间 + 其中一行是解绑留下的 0 份额 → 抬房必须被拒」的真库反例。

**已排除的第三处**：`orders.service.ts:17796`（套餐改档）同样没接，但
`resolveChangeableBundleRow` 在 `:25032-25041` 把「任一酒店/套餐行已落真实酒店」的单整体拒了，
而共享成员必须挂真实酒店行（§三）→ 带 0 份额遗留的单根本进不了改档。**不可达，不用改**，
但建议在那处补一行注释说明「靠 settled 闸兜住，不是漏了」。

## N2 · MEDIUM — `isLeftoverOnlyResubmit` 只校验「列出来的没改」，不校验「有没有漏列」→ 能现场把 Σ=1 的房做成孤儿房

**证据**：`hotel-control.shared-rooms.ts:906-916`

```
room.groups.length > 0 && room.groups.every((g) => isUnchangedMember(room.sharedRoomId, g))
```

`every` 遍历的是**请求体里的组**，落库现状里没被列出来的成员完全不参与判定。

**反例**：落库 S = A(份额 1) + B(份额 0)（这正是 §十五拍板 1 的默认形态）。请求把 S 明确
列进 `body.rooms`，但 `groups` **只写 B(0)**：
- `totalFraction = 0`，`every(isUnchangedMember)` 对 B 成立 → `isLeftoverOnlyResubmit = true` → **放行**（修复前这里是 400）；
- 落库段 `:1356 deleteMany({ sharedRoomId })` + 只按 `room.groups` 重建 → **A 被摘出成员表**；
- A 的 JSON 组也没了（`kept` 过滤器 `:988-994` 对 `touchedSharedRoomIds` 的组一律整体丢弃，而 S 是显式触及、不在 `implicitRoomIds` 的留守重建范围内）→ A 的 `roomsBilled` 被显式写 0。

净效果：一间真房，原本 A 付钱；一次请求之后**两张单都计 0 间**，钱凭空蒸发一间房的应收。
commit body 写的「只是把既成事实原样交回来，不是新增/改动」对这个输入**不成立**。

**缓解（不是消除）**：M6 的差集 warning 会报「已从共享房 X 移除 1 名成员：<A 单号>」，
H1 的孤儿 warning 也会报——两条都只是提示，不阻断；端点是 `requireStaff`，正常工作台
不会构造这种 payload（它按渲染的房间全量提交）。所以是 MEDIUM 不是 HIGH。

**修法**：`isLeftoverOnlyResubmit` 再加一个条件——本次列出的成员必须**覆盖落库现状的全部成员**
（`currentMembersByRoom.get(sid)` 的 `(orderId:orderItemId)` 键集合与乘客集合都被完全覆盖），
有漏列就仍然走 Σ≠1 的 400。补一条「漏列计费方 → 400」的反例。

## N3 · MEDIUM — H1④ 放宽了后端，前端 Σ=1 硬闸没跟着改：这条分支从 UI 永远走不到

**证据**：`admin-web/src/components/SharedRoomWorkbench.tsx:576-584`

```
const totalFraction = roundHalf(groups.reduce((s, g) => s + g.roomFraction, 0));
if (totalFraction !== 1) { setSaveErr(`房间「…」的计费份额合计须为 1，当前为 ${totalFraction}`); return; }
```

这个闸在 `roomsToSave` 上跑，请求**根本发不出去**。而 H1④ 的立意正是
「运营手上拿到的就是这间房的当前真实状态，硬拒没有可操作的出路」——后端给了出路，
唯一的 UI 把它挡在了本地。表现：运营打开工作台，想给一间孤儿房（Σ=0）改个房型或备注，
按保存 → 前端红字「计费份额合计须为 1，当前为 0」，与修复前**一模一样**。

（未改动的孤儿房不受影响：`:561` 的「没碰过就不重提交」会跳过它，不会误报。
隐式路径的 warning 也确实能显示——`:620` 把 `result.warnings` 拼进成功提示。）

**修法**：前端同步放宽成「Σ=0 且本房全部成员与 seed 完全一致 → 放行提交，把后端 warning 显示出来」；
或者反过来在 UI 上把这类房标成只读「孤儿房，请先解散或补一名计费方」。二选一，
但不能一边后端放行一边前端硬拦——本项目已经在「权限只提后端、前端仍只读」上栽过一次。

## N4 · MEDIUM — M4 的 fail-closed 会挡住一个系统自己造出来的自然形态

**证据**：`orders.service.ts:19211-19220`。触发条件 = 「该行既有带乘客的普通组、又有被本次
拆走人的共享组」。

**这个形态不是脏数据，是主路径产物**：一条酒店行住着 X、Y 两人，运营把 X 拖进跨单共享房 S
→ `kept` 过滤器把原普通组的乘客收窄成 `[Y]`（`hotel-control.shared-rooms.ts:1003-1007`），
该行从此就是「普通组[Y] + 共享组[X]」。此后只要拆单动到 X，就 400。

错误文案给的两条出路里，「把普通房组挪到别的订单行」对单酒店行订单做不到；
「把两者都并入同一间共享房」可行但要运营先想明白。

**建议**：至少 ①把文案改成以可行出路为主（引导去共享房合并 / 先把 X 从共享房解绑再拆）；
②在 §九 与操作手册里写明这条限制；③中期看能不能算出普通组那部分的默认搬走量而不必拒。
安全方向没错，不阻断合并，但**必须进部署前知会**，否则运营会在拆单时突然撞墙。

## N5 · MEDIUM — M5 接线顺手把恢复路径的库存锁范围放大了一大截

**证据**：`hotel-control.service.ts:1586-1602` 的 `lockRandomTierInventoryForUpdate`

```
SELECT id FROM "HotelBlockPeriod" WHERE "hotelId" IN (<该星级全部真酒店>) ORDER BY id FOR UPDATE
```

**没有日期过滤**。被替换掉的 `lockRandomTierBlockPeriodsWithinTx`（`:2151-2157`）是有
`dateFrom <= to AND dateTo >= from` 的。`lockHotelInventoryForUpdate`（`:1548-1553`）同理，
锁该酒店**全部**周期行。

后果：一次「恢复已取消订单」会把该星级**所有真酒店的所有历史/未来包房周期行**锁到事务结束。
线上一个三星档可能有十几家酒店 × 几十条周期。并发的建单 / 改期 / 换酒店只要碰到其中任何一家
就排队。功能正确（锁多了不会放行超卖），但是**交互路径上的争用面被显著放大**，
并且与按日期收窄的其它锁点混用时，死锁窗口也变大（同一张事务先按 hotelId 升序锁单店、
再用一条跨店语句按 period id 锁——两个并发恢复若酒店集合交叉，加锁顺序可能成环）。

**修法**：给这两个函数传本次涉及的日期并集（`min..max`）做区间过滤，advisory-lock 兜底逻辑保持不变；
或者把随机档变体改成「按 hotelId 升序逐店锁」，与 `lockHotelInventoryForUpdate` 同形，消掉环。
