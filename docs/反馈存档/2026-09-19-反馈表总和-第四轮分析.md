## 一、两条新增

### #5 运营·订单管理「导出整月数据 - 报错、不支持」 —— ✅ 真缺陷，已复现并定位

**复现**（测试站，ADMIN 令牌，`GET /orders/export-templates?template=full`）：

| 出行日期区间 | 结果 |
|---|---|
| 09-01 → 09-04 | 200，237 KB，7.0s |
| 09-01 → 09-07 | 200，416 KB，14.1s |
| 09-01 → 09-08 | 200，472 KB，15.1s |
| 09-01 → 09-09 | 200，525 KB，15.6s |
| **09-01 → 09-10** | **500**，4.8s（连试两次都 500，确定性） |
| 09-01 → 09-12 / 09-14 / 09-30 | 500 |
| 单日（09-08 / 09-09 / 09-10 各自） | 200，约 66–69 KB，4.3s |
| 09-08 → 09-10 | 200，178 KB，8.0s |

→ 不是某一天有脏数据，是**一次取回的总量过了硬天花板**；九月这个单量下天花板落在 9 天左右。

**根因**（测试站 backend 日志原文）：
```
prisma:error Invalid `prisma.order.findMany()` invocation:
Failed to convert rust `String` into napi `string`
  at async buildOrderTemplateExportWorkbook (dist/modules/orders/orders.export-templates.js:1037)
```
`Failed to convert rust String into napi string` = Prisma 查询引擎把整份结果序列化成**单个 JSON 字符串**回传 Node，字符串超过 napi/V8 上限直接失败。不是超时、不是内存限额（宿主 7G 空 4G，容器没设 limit，backend 常驻仅 100 MB），也不是 null 解引用。

**闯祸的那行**：`backend/src/modules/orders/orders.export-templates.ts:1388`
```ts
const fetched = (await client.order.findMany({
  where, orderBy: { createdAt: 'desc' },
  include: { agent, user, passengers, payments, refunds,
             items: { include: { flightSchedule:{include:{flight}}, hotelRoomType, visa, transfer, bundle, fulfillmentTasks } } },
}))
```
一次裸查、无 `take`、七层嵌套 include，payments/refunds 也整份拉。

**同病的还有《全岗总表》**：同样区间 `GET /orders/export/master?travelFrom=2026-09-01&travelTo=2026-09-30` → 500，日志堆栈
`at async buildMasterExportWorkbook (dist/modules/orders/orders.export-master.js:695)`，源码 `backend/src/modules/orders/orders.export-master.ts:924` 同款裸查。
`grep 'take:' backend/src/modules/orders/orders.export*.ts` 零命中 —— 按筛选导出这条路**全线没有任何条数上限**，`orders.export-intake.ts:180`、`orders.export-visa-bundle.ts:125`、`orders.export-room-allocation.ts:961` 是同一写法，只是列少、天花板更高。
按钮 title 还写着「按上方筛选导出命中的全部 N 条（不只是当前页）」（`OrdersPage.tsx:1487`）—— 产品意图就是支持整月，属于**崩了**，不是「不支持」。

**最小修法**：先 `findMany({ where, orderBy, select:{id:true} })` 拿全部 id，再按 id 分批（每批 150–200）带 include 取回、按原顺序拼接，下游 `filterExportOrders` 及所有口径一个字不动。两个文件各改一处。
顺带：单日就要 4–15 秒，include 里 `payments`/`refunds` 对 full/ticketing 模板是否真的每列都要，值得顺手收一收。

**给运营的临时话术**：目前一次导 7 天以内稳过；整月请分四次导（1–7 / 8–14 / 15–21 / 22–30）。

### #7 房控「跨单分房里面没有随机酒店的选项，随机酒店的客人不能分在一起」 —— ⚠️ 属实，但当前是方案里写死的排除项

不是 bug，是 `docs/跨单分房-需求方案.md:205` 明确拍过的：「共享房只允许真实酒店真实房型，占位酒店 / 随机档待落位不参与」（同文 :27、:55 重复）。

三道闸各挡一层，对上了运营的每一句话：
1. 下拉框直接滤掉随机档 —— `admin-web/src/components/SharedRoomWorkbench.tsx:219` `setHotels(r.hotels.filter((h) => h.randomTierPlaceholder == null))` → 这就是「没有随机酒店的选项」。
2. 未落位随机档（`OrderItem.hotelRoomTypeId=null` + `randomStarTier=3|4`）在任何酒店下都捞不出来 —— 候选查询 `backend/src/modules/hotel-control/hotel-control.shared-rooms.ts:159` 是 `hotelRoomType:{ hotelId }`；保存端二道闸 `:895-897` 直接 400「是未落位的随机档，不能跨单分房」。
3. 占位酒店硬传 id 也 400 —— `hotel-control.shared-rooms.ts:646-653`「占位酒店不参与跨单分房，请先把随机档落位到真实酒店」。

**为什么不能顺手放开**：`SharedRoom.hotelId` / `hotelRoomTypeId` 在 `schema.prisma:1290-1291` 都是**非空必填**，随机档没有真酒店可填 → 绕不过去的 schema 改动 + 迁移。
另外方案里「换酒店自动解绑共享房」（:126）会在落位那一刻把房拆掉，等于白做。

**两条路，要拍板**：
- A（大）：给共享房加「档次房」表示，候选查询支持 `hotelId | randomStarTier` 二选一（现成写法可抄 `hotel-control.schemas.ts:137-145` 的 `occupantsQuerySchema`），放开三道闸 + 前端两处 filter。要迁移。
- B（小，建议先问运营够不够）：随机档阶段不建共享房，改成**落位时按同住组一起落**。系统里已有 `Order.sameHotelWith`（同酒店安排），工作台也已经读了它（`hotel-control.shared-rooms.ts:174`）；只要加一个「按同住组批量换酒店」，落位后自然就能跨单分房。改动小一个数量级。

### #2 飞行次数 —— 🔴 未修改，且不建议照原话做

口径没变，仍是 **可用 = 已飞 − 已核销**，在订未飞只展示不计入：
- `backend/src/modules/travelers/traveler-benefits.service.ts:72-78`、核销校验闸 `:113-124`
- 前端 hover 原文 `admin-web/src/pages/OrdersPage.tsx:1105`「可用 = 已飞 − 已核销；在订未飞不计入可用」
- 设计理由写在 `traveler-profiles.aggregate.ts:9-15`：「客人没飞却拿到一次额度等于白送」

「要在哪里扣」—— **有地方扣**：常旅客档案详情抽屉 →「核销权益」按钮（`TravelerProfilesView.tsx:1013-1064`），台账与冲正都在同一抽屉；0918 刚上线订单页乘客名直达档案（a1f3eb8）。

**真正的缺口**：录单时勾的「次数升级」（`Passenger.upgradeRedeemLeg`，`schema.prisma:2089`）**只是个标签**，全仓零处与核销台账（`TravelerBenefitRedemption`）交叉引用 —— 标了升级之后系统既不自动扣、也不提醒去扣。运营问「在哪里扣」，问的其实是这座没搭的桥。

**按原话改会出事**：`pendingTripCount` 的统计口径**包含待支付单**（`traveler-trip-count.ts:43-49`，`EXCLUDED_ORDER_STATUSES` 不排除待支付）；核销台账 append-only 无自动冲正。把在订未飞算进可用 → 一张没收钱的单就能换出一次升舱 → 单子取消后权益收不回来 = 超发。
另：`tripCount - redeemedTrips` 这个减法在后端有 **9 处内联重复**（traveler-benefits ×2、traveler-profiles ×4、export-master ×2、export-trip-stats ×2、export-templates ×1）+ 前端 5 处，真要改口径得全部一起动。

**正解**：口径不动；补「标了次数升级 → 起飞后生成一条待办提醒去核销」，或在订单页那个标记旁加「去核销」直达（复用 0918 的 `travelerProfileLink.ts`）。若运营坚持要下单时就锁额度，那是新建「预留/冻结」机制 + 取消自动释放，另立项。
