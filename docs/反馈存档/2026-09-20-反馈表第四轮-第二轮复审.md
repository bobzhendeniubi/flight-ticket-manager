## 二、对抗式证伪（A–G）

### A. finding 1 短修

- **锁序**（内存反例 A，成员表插入顺序 B、A，兄弟房 `room_a` < 目标 `room_z`）实测：`Order ord_a → ord_b → ord_c`，再 `SharedRoom room_a → room_z`，再 `HotelBlockPeriod … ORDER BY id FOR UPDATE`。与 `saveSharedRoomsInner`（`hotel-control.shared-rooms.ts:498-500` Order 升序，`:865-866` SharedRoom 升序，周期最后）、`planUnbindMany`（`shared-room-unbind.ts:228-236` 调用方先持 Order 锁 → SharedRoom 升序）三者同一全局顺序，都是默认 `.sort()`（cuid 小写字母数字，ASCII 序一致）。**未发现反向锁序**：解绑路径只持单张 Order 锁再锁房，落位路径先锁全部 Order 再锁房，不会形成 Order↔SharedRoom 环。

## 三、新发现（按严重度）

### N1 ｜ HIGH ｜ 规则 12 自动核销后，同一把稳定键永远无法再生成（修出新问题）

- 位置：`backend/src/modules/reminders/reminders.rules.upgrade-redeem.ts:506-538`（只关不开）；`backend/src/modules/reminders/reminders.rules.ts:1489-1495`（`existing` 查重不带 status，DONE 行同样命中）；`backend/prisma/schema.prisma:2469`（`ruleKey @unique`）。
- 触发（三条真实路径，均为原地不换键）：
  1. 已飞航段被改期到未来（`rescheduleOrderItem` 原地 update，行 id 不变）→ 本轮 `STALE_NOTE_NOT_DEPARTED` 自动核销 → 新日期飞完 → 候选键与已 DONE 行同键 → `existingKeys` 过滤掉 → **永不再提醒**；
  2. 订单取消 → `STALE_NOTE_GONE` 核销 → `restore-cancelled` 恢复占位 → 同上；
  3. 台账已核销 → `STALE_NOTE_REDEEMED` 核销 → 财务冲正（负 `tripsUsed`）→ `redeemedAfterLeg=false` → 同上。
- 后果：规则 12 存在的目的（该扣没扣时喊一声）在这三种情形下静默失效，可用次数虚高。旧四段键把起飞日放进键里，路径 1 原本会生成新键——这是稳定键改造带来的回退。规则 11 为同类问题特意把 `returnReleased.at` 放进键（`reminders.rules.test.ts:1149`），说明代码库已知这个坑。
- 建议：照抄 `reconcileRoomAssignmentReminders` 的 `toReopen`——在 `reconcileUpgradeRedeemReminders` 里对 `desiredKeys` 命中、状态为 DONE 且 `resolvedNote ∈ {五条 STALE_NOTE_*}` 的行重开（`status: OPEN, resolvedAt/resolvedNote: null`，可顺带刷新 title/body/dueAt）；人工核销/跳过（备注是别的内容）仍尊重不重开。补三条回归：改期回未来再飞、取消再恢复、核销再冲正。
